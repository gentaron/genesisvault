# ADR-0016: 囲い（審査層）— 見逃しを設計で潰す（Phase λ）

**Status**: Accepted
**Date**: 2026-07-29
**Phase**: λ — The Enclosure
**Deciders**: gentaron

## Context

このパイプラインには檻（8エージェントの自作ループ）・餌（継続性台帳と参照コーパス）・
選別（人間のマージ）は揃っていた。弱かったのは**囲い**——出てきたものを検査する層だけだった。

具体的な症状が4つあった。

**1. 良いモデルが書き手に、安いモデルが審査役に配られていた。**

| 役割 | 変更前のモデル |
|------|--------------|
| Sophia（執筆・VE-002） | `gemini-2.5-flash` |
| Iris（校正・VE-006） | `gemini-2.5-flash-lite` |

配分が逆だった。書き手が雑でも、審査が厳しければ差し戻して直せる。
だが審査が甘いと、雑なものがそのまま外に出る。出た後で止める仕組みは無い。

そしてこの失敗は**画面に何も表示されない**。エラーも警告も出ず、全部緑で通る。
見逃しは静かで、誤検知はうるさい。だから運用していると誤検知だけが目につき、
見逃しは永久に発見されない。非対称なコストには、非対称な配分で応える必要がある。

**2. 品質ゲートが満点を出した記事が、実は中身が無かった。**
決定論ゲートは文字数・体裁・語彙しか見ていない。
「どの日にも貼り替えられる一般論」は、そのすべてを通過して100点を取る。

**3. 審査役が甘い採点をできる構造だった。**
`brief-gate.mjs` はモデルに `score` を直接出させ、その数字で合否を決めていた。
採点者が自分の点数を申告する仕組みは、甘くなる方向にしか壊れない。
また、指摘に根拠の引用を求めていなかったので、当たり障りのない講評でも通ってしまう。

**4. ゲートが開けっ放しになる経路があった。**
企画指示が無いと審査自体をスキップして `exit 0`。
落ちた原稿は `unlink` で削除され、なぜ落ちたかを後から検証できなかった。

そして最大の問題は、**ゲートの実力を誰も測っていなかった**こと。
捕捉率が9割なのか3割なのかを知る手段が無かった。

## Decision

### 1. 審査役に最強モデルを置く（配分の反転）

Iris（VE-006）を `gemini-2.5-flash-lite` → `gemini-2.5-flash` に。
温度は 0.3 → 0.2。ティアは `precision` とは別に `judge` を新設した
（校正者は直す人、審査役は落とす人。役割が違えば配線も違う）。

書き手（VE-002）は**触っていない**。上げるべきは淵であって中身ではない。

さらに、この配分が将来また逆転しないよう、**設定の整合性チェックで機械的に禁止**した。
審査役の最優先モデルが書き手より弱いと `bun run verify` が落ちる。

### 2. 審査ロジックをライブラリ化し、5つの防御を入れる（`src/lib/pipeline/review.ts`）

**(a) モデルは観察し、コードが決める。**
判定モデルは項目ごとの観察だけを返す。総合点も合否も返さない。
加重集計は `computeVerdict()` が rubric の重みから決定論的に行う。
**採点者が出さない数字については、甘くなりようがない。**

**(b) 証拠の実在検証。**
減点には原稿からの逐語引用を要求し、`verifyEvidence()` が
その引用が本当に原稿に含まれるかを照合する。実在しない引用を出した指摘は破棄する。
引用を捏造する審査役は「厳しい」のではなく「当てにならない」。
**この検証自体はモデルを使わない**ので、審査役の信頼性を決定論的に測れる。

**(c) veto 項目。**
テーマのすり替え（`theme_drift`）と事実の逆行（`internal_consistency`）は
加重平均に参加させず、一発不合格にする。
5項目が良ければ1項目の致命傷が薄まる、という構造を排除した。

**(d) fail-closed。**
プロバイダーが無い・全滅した・不正な出力しか返らない——すべて**不合格**として扱う。
審査できなかった原稿は通さない。閉じられないゲートは、閉じたことにする。

**(e) 独立性。**
審査役には企画指示と成果物しか渡さない。過去記事・テーマバランス・文体サンプルは渡さない。
書き手の文脈を持った審査役は、外部審査ではなく自己評価になる。
`buildJudgePrompt()` に執筆文脈が混入しないことを**テストで固定**した。

加えて、未報告の項目は 0 点として扱う（沈黙を合格と読まない）。
合格ライン付近（±10点）では別プロバイダーによる二重審査を行い、低い方を採る。

### 3. 落ちた原稿は隔離し、判定は全件記録する

`unlink` をやめ `.gate-quarantine/` へ退避、判定 JSON を併置。
通過・差し戻しの両方を `docs/gate-runs/YYYY-MM.md` に記録する。
**「何を落としたか」だけでなく「何を通したか」を残さないと、見逃しは検証できない。**

### 4. ゲート自身を測る（これが本丸）

`tests/fixtures/gate/` にゴールデン事例集を置いた。既知の不良7件＋正常1件。
各事例には「どの検査が捕まえるべきか」が宣言されている。

- `tests/gate-calibration.test.ts` — 決定論層の捕捉を毎回検証（LLM 不要、`verify` に含む）
- `scripts/gate-eval.mjs`（`bun run gate:eval`）— 審査役の捕捉率・誤検知・捏造引用を測定（APIキー必須）

特に重要なのが `blindspot` 種別の2件。
**決定論では原理的に捕まえられないと分かっている事例**を、意図的に置いてある。

| 事例 | 内容 | 受け皿 |
|------|------|-------|
| `blindspot-generic-but-clean.md` | 体裁は完璧だが、その日にしか書けないことが何も無い | `concrete_specificity` |
| `blindspot-theme-drift.md` | 指示は「つみたてNISA」、中身はコーヒーの淹れ方 | `theme_drift`（veto） |

決定論テストはこの2件が**通過してしまうこと**を明示的に固定している。
これは成功ではなく限界の記録で、審査役が唯一の防波堤であることを可視化するためのもの。
`verify` は「死角に審査側の受け皿が宣言されているか」も確認する。

正常系の対照群（`good-concrete-diary.md`）も必須にした。
不良しか置かないゲートは「全部落とす」で満点になり、
厳しすぎるゲートは運用で緩められて最終的に無効化される。

## Consequences

**得られるもの**

- 審査役の見逃しが、静かではなく**測定可能**になった（`bun run gate:eval`）
- 甘い採点・捏造引用・沈黙による素通りが構造的に潰れた
- 配分の逆転が設定チェックで再発しなくなった
- 判定の全履歴と差し戻された原稿の実物が残る
- 審査ロジックが APIキー無しでテストできる（判定系だけで 33 テスト）

**代償**

- 審査コストが上がる。強いモデルを使い、境界帯では2回呼ぶ
  （ただし審査は1記事1回で、執筆より短い。無料枠の範囲で収まる想定）
- fail-closed なので、プロバイダー障害時は記事が出ない。
  静かに悪いものを出すより、何も出さないほうがよいという判断
- ゴールデン事例集の保守が必要。見逃しを見つけたら事例を足す運用が要る

**やらなかったこと（非目標）**

- 書き手のモデル変更 — 上げるべきは淵。中身ではない
- 決定論ゲートで「一般論かどうか」を判定すること — ルールでは原理的に無理。
  死角として記録し、審査役に渡すのが正しい切り分け
- `gate:eval` を `verify` に入れること — ネットワークと APIキーが要るため、
  「オフラインで同じ答えが出る」という verify の性質（INV-004）を壊す
- Biome / 型エラーの既存バックログ整理 — 引き続きラチェット管理
