# ADR-0017: 記事から動画への受け渡し — Linear を境界にする（Phase μ）

**Status**: Accepted
**Date**: 2026-08-04
**Phase**: μ — The Handoff
**Deciders**: gentaron

## Context

Genesis Vault は毎日 1 本の記事を生成し、VAIZ（`gentaron/VAIZ`）は Linear の
`agent-ready` + Todo の Issue を 1 件 claim して短尺動画を作る。この 2 つは
既に個別に動いていたが、**間が人間だった**。記事が出るたびに、人が Linear で
GEN-6 / GEN-7 のような動画ブリーフを手で書いていた。

その手作業を機械に渡すのが本 ADR の対象。ただし単に自動化すると、
これまで人間が担っていたものが 2 つ同時に消える。

1. **企画の判断** — 記事のどの論点を動画にするか
2. **着手の承認** — `agent-ready` ラベルを貼るという行為そのもの

(2) は無視できない。`agent-ready` のラベル説明には
「人間による着手承認ゲート。貼れるのは人間のみ」と書いてあり、
GEN-6 の動画ブリーフ自体が「エージェントに承認ゲートが要る理由」という内容だった。
その運用を自動化するのだから、**何がその役目を代わりに果たすのか**を
決めずに進めることはできない。

さらに、この経路の失敗は静かである。間違ったブリーフを 1 件置くと、
その晩に間違った動画が 1 本できる。Issue は正常に作られ、
ワークフローは緑で終わり、誰にも何も表示されない。
INV-011 で扱った「見逃しは何も表示しない」問題が、そのまま再現する形をしている。

## Decision

### 1. 境界は Linear。両リポジトリは互いを知らない

VAIZ を直接叩かない。Genesis Vault は Linear に Issue を置くだけ、
VAIZ は Linear から Issue を拾うだけ。契約は
**「Todo + `agent-ready` + GEN-6/GEN-7 と同じ見出し構成」** の 1 つだけである。

この形にしたので、Issue の供給元が人間でも VE-009 でも VAIZ 側は区別しない。
上流を増やしても下流の変更は要らないし、片方を止めてももう片方は動く。

### 2. VE-009 Runa Vogel（Briefer）を新設する

記事 → ブリーフの変換はモデルの仕事なので、既存 8 体と同じ扱いにした。
名簿・ルーティング・プロンプトはすべて `config/pipeline.json` と
`prompts/runa/` にある（INV-001）。ID は VE-009 で、既存 ID は動かしていない（INV-006）。

### 3. モデルは中身だけを返し、骨格はコードが組む

Runa が返すのは 5 フィールド（`video_title` / `theme` / `points` / `tone` /
`visual_direction`）だけで、Markdown は 1 文字も返さない。
見出し構成・タイトル接頭辞・「45〜60秒、縦型。6〜8シーン。」は
`src/lib/pipeline/video-brief.ts` が config から組み立てる。

想定尺とシーン数は VAIZ の `PlanSchema` が実際に強制する受け入れ条件であって、
この動画についての意見ではない。**モデルが別の Markdown を書くことで
交渉できてしまう場所に置かない。** INV-013（合否はコードが決める）と同じ理由。

### 4. 人間の承認ゲートを、機械的な 4 つの制約で置き換える

`agent-ready` を機械が貼る以上、それが防いでいたもの——
暴走したエージェントが無料枠を食い潰し、誰も見ていない成果物を積み上げること——
を別の手段で防ぐ必要がある。すべて **Issue を作る前** に置いた。

| 装置 | 何を防ぐか | 実装 |
|------|-----------|------|
| 冪等性 | 同じ記事から 2 本目の動画 | 台帳 + Issue 本文の `gv:source=` マーカー |
| 背圧 | 消化されないキューの無限成長 | Todo の未着手件数が `maxQueued` 以上なら積まない |
| 検証 | 中身が壊れたブリーフの投入 | `lintVideoBrief()` を通らなければ作らない |
| 転載検出 | ゲート記事本文の外部流出 | 記事本文との逐語一致が閾値を超えたら作らない |

冪等性の正典は **Linear 側の Issue** であって台帳ではない。
台帳のコミットが失われても二重に生えないよう、実物を毎回見に行く。
逆に台帳だけを見て済ませると、コミット漏れの日に 2 件目が生える。

### 5. ブリーフ生成は fail-closed。テンプレートに落とさない

他のエージェントは全滅時にテンプレートへフォールバックする（AGENTS.md §10.4）。
Runa はしない。Nova のフォールバックは「少し悪いテーマ」で済むが、
Runa のフォールバックは **`agent-ready` を貼られたテンプレートのブリーフ**であり、
別リポジトリの無人パイプラインが一晩かけてそれを動画にする。
出来上がるまで誰も気づかない。

ブリーフが 3 回とも検証を通らなければ、Issue を作らずに終わる。
記事は既に生成・検証・push 済みなので、失うものは無い。

### 6. Linear への送信は記事の公開をブロックしない

ワークフローのブリーフ工程は `continue-on-error: true`。
Linear の障害で、書けている記事が赤いビルドになる理由は無い。
逆に、スクリプト側は壊れた状態で Issue を作るくらいなら
非ゼロで落ちる——「Issue が無い」は常に安全側だからである。

### 7. VAIZ への通知は最適化であって前提ではない

`VAIZ_DISPATCH_TOKEN` があれば `repository_dispatch` で VAIZ を即起動する。
無ければ飛ばないだけで、VAIZ の 22:00 UTC の cron が同じ Issue を拾う。
**トークンの有無で経路の成否が変わらない**ようにしてある。

## Consequences

### 得られたもの

- 記事 → 動画が人手を介さずに繋がった
- 上流（人間 / VE-009）と下流（VAIZ）が Linear 越しに疎結合のまま
- ブリーフの構造・尺・シーン数が config の 1 箇所で決まる
- 失敗の既定値が「何も作らない」になった

### 失ったもの / 引き受けたリスク

- **`agent-ready` は人間専用ではなくなった。** ラベル説明の文言と実態がずれる。
  Linear 側の説明を書き換えるのは人間の作業として残っている
- 背圧の閾値（`maxQueued`）は勘で決めた値である。
  Todo が慢性的に詰まるようなら、VAIZ 側の消化能力に合わせて調整する
- 重複検出は Linear の新しい 100 件しか見ない（`orderBy` に方向指定が無いため）。
  それより古い記事の再送は台帳だけが守っている
- `--no-agent-ready` / `GV_LINEAR_AUTOSTART=false` で人間ゲートに戻せるが、
  戻したことに気づく仕組みは無い（Todo にラベル無しの Issue が溜まるだけ）
