# ADR-0018: 外の景色を取り込み、到達点を後退させない（Phase ν）

**Status**: Accepted
**Date**: 2026-08-05
**Phase**: ν — Trend Radar & Continuity Gate
**Deciders**: gentaron

## Context

要求は2つ、方向が逆を向いている。

1. **外を見る** — 記事を書くとき、AI・最先端技術の話題と株式市場のトレンドを
   取り込む。毎日同じ井戸から汲んでいると、記事が世界と無関係になる。
2. **過去と揃える** — 「貯金300万円」と書いた次の記事で「貯金200万円達成」と
   書かない。金額に限らず、あらゆる話題でこのばらつきを無くす。

(2) の仕組み自体は Phase ι で入っていた（Vera → Edda → Mira と継続性ブリーフ）。
それでも実際の記事コーパスには逆行が残っていた。調べると、原因は3つあった。

- **台帳が凍っていた**。ファイルが在ればそのまま使う実装で、しかも日次ジョブが
  台帳をコミットしていなかった。毎晩更新して毎晩捨て、翌朝また古いものを読む
  循環が成立していた（LM-013）
- **台帳が逆行を追認していた**。最高到達点は守られていたのに、出来事の一覧には
  「貯金300万達成」の13日後に「貯金200万達成」が並んでいた（LM-014）
- **金額しか見ていなかった**。「積立3年目 / 4年目 / 5年目」が記事ごとにばらつき、
  誰も止めていなかった

そして最大の問題は、**ブリーフに「逆行するな」と書いてあるだけだった**こと。
指示が守られたかどうかを確認する仕組みが無く、破られても画面には何も出ない。
INV-011 で扱った「見逃しは何も表示しない」が、そのまま継続性でも起きていた。

## Decision

### 1. トレンド・レーダーは新しいエージェント（VE-010 Tessa Brandt）にする

役割が増えたのだから名簿に載せる。工程の先頭（step 1）に置き、
Hacker News・arXiv・Stooq から「今日の外の景色」を集めて
Nova（テーマ選定）/ Lena（企画）/ Sophia（執筆）に渡す。

集めるのは決定的な処理で、LLM は使わない。相場は**予測しない** — 5営業日の
変化率と20日移動平均との位置関係という、見ればわかることだけを言葉にする。

### 2. トレンド取り込みは fail-soft。審査層とは正反対にする

`review.ts` は「審査できなければ通さない」（INV-012）。トレンドは逆で、
「取れなければ黙って諦める」。HN が落ちている日に日記が出ないのは、
明らかに割に合わない。失敗は `degraded` として記録し、パイプラインは続行する。

ソースは API キー不要のものだけ（INV-003 と同じ理由）。
`bun run verify` からは絶対に呼ばない（INV-004）。

### 3. トレンドには必ず「使い方」を添えて渡す

材料だけ渡すと日記がニュース要約や相場解説に化ける。それは Genesis Vault の
記事ではない。ブリーフの本体は制約のほうで、何を書かないかまで書く。

- 記事の入口に使う材料であって、主題ではない（触れるとしても1〜2文）
- 相場の予想・投資助言・個別銘柄の推奨は書かない
- レーダーの数字をミナ自身の貯金額・資産額として書かない

最後の1行は継続性と直結している。「日経平均4万2000円」が個人の貯金額として
台帳に入ると、到達不能な下限が居座り、以後すべての原稿が逆行判定で落ちる。
抽出側にも相場語の除外（`MARKET_NOISE`）を入れて二重に防ぐ。

### 4. 継続性は「指示」から「ゲート」に格上げする

ブリーフは残す（先に伝えるほうが安い）。そのうえで決定的なチェックを3箇所に置く。

| どこで | 何をするか |
|--------|-----------|
| 書き手の原稿 | 逆行を検出したら、**具体的な指摘つきで1度だけ書き直させる** |
| 校正後の本文 | Iris は本文を書き換えるので再確認。残っていればパイプラインを落とす |
| テンプレート | フォールバックの本文・タイトルも同じ述語で選別する |

3番目は忘れやすいが、**AI が全滅した日にだけ逆行が出る**のが一番見つけにくい
壊れ方なので外せない。

書き直しには「前回どこが駄目だったか」と直し方（数値を上げる / 回想として書く）を
渡す。フィードバックの無い再試行はサイコロの振り直しにしかならない。

### 5. 逆行を見る対象を、金額から全指標へ広げる

`CONTINUITY_METRICS` に単位（円 / 日 / 年 / 冊）を持たせ、金額・習慣の継続日数・
継続年数・読了冊数を同じ枠組みで扱う。読了冊数のように年でリセットされる指標は
`scope: 'year'` にして、台帳のキーに年を含める（1月が逆行にならないように）。

増やすときの原則は **取りこぼしは安いが、誤検出は高い**。拾い損ねた事実は
その日の縛りが1つ減るだけだが、誤って拾った事実は台帳に居座り、以後の原稿を
毎日落とし続ける。だから主語と数値の近接を要求し、曖昧な言い回しは拾わない。

### 6. 台帳は毎回作り直す（導出できるものは導出する）

キャッシュを信じるのをやめ、`src/content/posts` から毎回組み立てる。
走査は 170 本強のローカルファイルで、LLM もネットワークも要らない。
あわせて日次ジョブの `git add` に台帳とレーダーのスナップショットを足した。

## Consequences

**得られたもの**

- 逆行は「起きても分からない」から「起きたら止まる」になった
- 金額以外の指標（積立年数・瞑想日数など）にも同じ保証がかかる
- 記事が外の出来事に接続される。テーマ「AI・テクノロジー」も追加した

**代償**

- 外向きの通信が増えた（1日あたり最大8リクエスト、上限8秒）。fail-soft なので
  落ちても記事は出るが、監視対象が1つ増えた
- 台帳を毎回作り直すぶん、生成の先頭で数百ミリ秒使う
- 誤検出があると原稿が落ちる。落ちてもテンプレートに退避するので記事は出るが、
  検出規則を足すときは慎重に（§5 の原則）

**やらなかったこと**

- 相場の予測・売買シグナルの生成。日記が投資助言に化ける
- トレンドを記事の必須入力にすること。外部サービスの死活が公開の可否を握る形は
  割に合わない
- 過去記事の遡及修正。既に公開したものは歴史として残す（ADR-0016 と同じ姿勢）
