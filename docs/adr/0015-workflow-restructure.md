# ADR-0015: ワークフロー再構成 — 宣言的設定・契約としての仕様・決定論的検証・記憶インフラ（Phase κ）

**Status**: Accepted
**Date**: 2026-07-28
**Phase**: κ — Workflow Restructure
**Deciders**: gentaron

## Context

このリポジトリは「AI が記事を生成する」部分はよく整備されている（8エージェント、
6プロバイダーのフォールバック、品質ゲート、継続性台帳）。一方で、**AI が働くための
環境**のほうは、コードの成長に置いていかれていた。具体的な症状:

1. **設定が4ファイルに散っていた** — ルーティング表は `routing.ts`、品質ゲートの閾値は
   `quality-gate.ts`、プロバイダーチェーンは `providers.ts`、参照ファイル名は `shared.ts`、
   開発ルールは `AGENTS.md` の HTML コメント。「Writer の temperature を下げる」だけで
   人間も AI も TypeScript を読み、正しい定数を探し当てる必要があった。

2. **仕様を書く場所が無かった** — `.github/` に Issue テンプレートも PR テンプレートも
   存在しなかった。受け入れ条件と非目標が構造化されていないため、
   「どこまでやれば完了か」が実装者の解釈に委ねられていた。

3. **検証の入口が無かった** — `lint` / `test` / `astro check` は個別に存在したが、
   「これを実行して緑ならマージしてよい」という単一のコマンドが無かった。
   生成された記事に対する決定論的なチェックも、コミット前には走っていなかった。

4. **記憶が索引化されていなかった** — ADR は14件あるが番号が3組衝突しており
   （0006/0008/0010）、「ADR-0010 を見て」が2つの別文書を指していた。
   不変条件と既知の地雷を書く場所も無かった。

背景として、生成コストが下がり検証コストが相対的に上がった以上、価値は
「コードを書けること」から「受け入れ条件を定義できること・品質ゲートを設計できること」へ
移っている。リポジトリの構造もそれに合わせる必要がある。

## Decision

4つの変更を行う。**既存の生成パイプラインの挙動は一切変えない**（純粋な構造変更）。

### 1. `config/pipeline.json` を唯一の宣言的ソースにする

エージェント名簿・プロバイダーチェーン・ルーティング・品質ゲート閾値・参照ファイルを
1枚の JSON に集約し、`src/lib/pipeline/config.ts` が Zod で検証して読む。
TypeScript 側は**自前の既定値を持たない**（不正な設定は起動時に例外で落とす。
黙って既定値に落ちるのは設定ミスを隠す挙動なので採らない）。

スキーマだけでは表現できない参照整合性（ルーティングが存在しないプロバイダーを指していないか、
エージェント ID が重複していないか、正規表現が壊れていないか）は
`checkConfigIntegrity()` で別途検査する。

`config/pipeline.schema.json` を Zod から生成して同梱し、エディタ補完を効かせる。
生成物なので Biome の整形対象から外す（→ LM-002）。

### 2. 仕様を契約として書かせる

`.github/ISSUE_TEMPLATE/feature.yml` は **受け入れ条件と非目標を必須欄**にする。
「〜が改善される」ではなく「〜したとき〜になる」と書かせ、マージ判断はそのリストだけを見る。
非目標欄を必須にするのは、スコープの無制限な拡大が実務上いちばん多い失敗だから
（AGENTS.md §2.5 の運用面での裏付け）。

PR テンプレートは「実装の説明」ではなく「契約が満たされた証明」を書かせる構造にする。

### 3. `bun run verify` — 決定論的な単一ゲート

**LLM・ネットワーク・API キーを一切使わない**検証を1コマンドに集約する:

- 設定のスキーマ検証と参照整合性
- 生成 JSON Schema のドリフト検出
- 記事コーパス163件の決定論的リント（`content-lint.ts`）
- ADR 番号の重複検出と INDEX の鮮度
- Biome / 型 / ユニットテスト

判断が要らないチェックを LLM に投げないための境界線でもある。硬い骨格で落とせるものは
全部そこで落とし、主観的な judgement だけをエージェントに残す。

Biome（105件）と `astro check`（17件）には既存の指摘が残っている。一括修正は85ファイルの
整形差分になり AGENTS.md §3.3（整形と論理変更を混ぜない）に反するため、
**ラチェット方式**（`config/quality-baseline.json`）を採る。増やしたら失敗、減らしたら基準を締める。

### 4. `docs/almanac/` — 記憶をインフラにする

- `INVARIANTS.md` — 壊してはいけない前提10件。各項目に「どう守られているか」を併記し、
  「人間の注意」しか書けない項目はテストに落とすべき候補として可視化する
- `LANDMINES.md` — 一度踏んだ罠6件を「症状 → 原因 → 回避策」で記録
- `INDEX.md` — ADR・Runbook から自動生成（手編集禁止、`bun run almanac` で再生成）

衝突していた ADR 番号は後発側を採番し直した（0006→0012 / 0008→0013 / 0010→0014）。
以後の重複は `bun run verify` が検出する。

## Consequences

**得られるもの**

- 設定変更が JSON 1ファイルの編集で済む。人間も AI も同じ場所を触る
- 設定ミスが起動時の例外になる（本番で静かに壊れない）
- 「マージしてよいか」が `bun run verify` の終了コードで決まる。CI とローカルが同一
- 受け入れ条件の無い Issue が構造的に作れない
- ADR 番号の衝突と INDEX の陳腐化が機械的に防がれる

**代償**

- 設定を1段階の間接参照越しに読むことになる（`routing.ts` を読んでも数値が無い）。
  各ルートに `why` を併記して補っている
- `config/pipeline.schema.json` と `docs/almanac/INDEX.md` という生成物が2つ増えた。
  どちらもドリフトを verify が検出するので、放置はできない
- ラチェットは既存の指摘を許容し続ける。締める作業は別途必要

**やらなかったこと（非目標）**

- Biome / 型エラーの一括修正 — 整形差分に本質的変更が埋もれるため別作業とする
- ペルソナ定義（`shared.ts` の日本語プロンプト）の JSON 化 — 散文であって設定ではない
- 生成パイプラインの挙動変更 — 本 ADR は構造のみを対象とする（テスト303件は変更前後で不変）
