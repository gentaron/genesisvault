# LANDMINES — 一度踏んだ罠

同じ穴に二度落ちないための記録。**症状 → 原因 → 回避策**の3点セットで書く。

新しく踏んだら、抜け出した直後に書くこと。翌日には「なぜハマったか」を忘れている。
ここに書けるくらい理解できていないなら、まだ直っていない可能性がある。

## LM-001: ADR の番号が3回衝突していた

**症状**: `docs/adr/` に `0006` が2つ、`0008` が2つ、`0010` が2つ存在した。
「ADR-0010 を見て」が2つの別文書を指し、README とコードコメントが別の ADR を参照していた。

**原因**: 番号を採番する仕組みが無く、並行して書かれた ADR が同じ次番号を選んだ。
ファイル名が違えば `git` は何も言わない。

**回避策**: 後発側を採番し直した（`0012` / `0013` / `0014`）。
`bun run verify` が番号の重複を検出して失敗するようになっている。
新しい ADR を書く前に `docs/almanac/INDEX.md` で最大番号を確認すること。

## LM-002: 生成した JSON を Biome が整形してドリフト扱いになる

**症状**: `bun run config:schema` で生成した `config/pipeline.schema.json` が、
`biome check --write` のあとテストで「Zod スキーマと不一致」と判定される。

**原因**: 生成側は `JSON.stringify(..., null, 2)`、Biome は独自の整形（短い配列を1行化）。
両者が同じファイルを奪い合い、どちらを実行したかで内容が変わる。

**回避策**: 生成物を Biome の対象から外す（`biome.json` の `!config/pipeline.schema.json`）。
**生成物は整形しない** — これは他の生成ファイルを追加するときにも効く原則。

## LM-003: `astro check` の型エラーは `@ai-sdk/*` の版ずれ（新規ではない）

**症状**: 何も壊していないのに `bunx astro check` がエラーを返す。

**原因**: `@ai-sdk/*` の各プロバイダーが `LanguageModelV3` を返すのに対し、
`ai` v5 の `LanguageModel` 型が `V2` を指しているという SDK 間のバージョン差。
実行時は動く。型だけが合っていない。

2026-08 時点で残っているのは **3 件のみ**（`cerebras` / `openrouter` / `huggingface`)。
かつて 17 件あったうち残り 14 件は SDK と無関係な実コードの問題で、すべて解消済み。
`google` と `groq` は V2 を返すので影響を受けない — **フォールバック連鎖 5 本のうち 3 本が
コア SDK と型不整合**という状態であることは意識しておくこと。

**回避策**: `as unknown as` で握り潰さないこと。実害はなく、SDK 側の更新で解消する種類の不一致で、
キャストするとSDK が本当に壊れたときに気づけなくなる。
`bun run verify` は**件数のラチェット**で管理している（`config/quality-baseline.json`）。
増やさなければ通る。減らせたらベースラインを締める。

## LM-004: Biome の指摘を一括修正したくなるが、やらない

**症状**: `bun run lint` が大量のエラーを返す。「まとめて `--write` すれば0になる」と思える。

**原因**: 残っている指摘の大半は整形（インデント・import 順・テンプレートリテラル・
`node:` プロトコル）で、機械的には直る。

**回避策**: やらない。理由は2つある。

1. AGENTS.md §3.3 が整形変更と論理変更の混在を禁じている。
   85ファイルの整形差分に本質的な変更が1行混ざると、レビューで発見できない。
2. **そもそも `--write` は安全ではない**。Astro ファイルに対する Biome の
   自動修正はページを壊す（LM-011）。

触ったファイルだけを `biome check --write <file>` で直し、
全体はラチェット（`config/quality-baseline.json`）で「増やさない」だけ担保する。

**意味のある指摘と整形の指摘は分けて考えること。** 2026-08 の棚卸しでは、
デッドコード（未使用の変数・import・書き込み専用の状態）と `any` と
banned type を実コードから除いて **105 → 94** まで落とした。

残る 94 件の内訳は **93 件が純粋な整形**（`format` 54 / `organizeImports` 39）と
`src/styles/app.css` の parse 1 件で、**意味のある指摘はもう残っていない**。
`noExplicitAny` はリポジトリ全体で 0 件になった。
つまりこれ以降ここが増えたら、それは新しく持ち込まれた指摘である。

**症状**: README に「192 ユニットテスト」と書いてあるが、実際は 336 件だった。

**原因**: テストは増え続けるが、README の数字は手で書かれていて誰も更新しない。

## LM-007: 良いモデルを書き手に、安いモデルを審査役に配っていた

**症状**: 実行ログを見ると Sophia（執筆）が `gemini-2.5-flash`、
Iris（校正）が `gemini-2.5-flash-lite`。品質ゲートは満点を出すのに、
中身の無い記事が通っていた。

**原因**: 「重い仕事＝執筆」という直感で配分していた。
`routing.ts` のティア名も `precision`（＝校正）で、審査という役割が言語化されていなかった。

**回避策**: 配分を反転し、`judge` ティアを新設した。
そのうえで **設定の整合性チェックで機械的に禁止**している——
審査役の最優先モデルが書き手より弱いと `bun run verify` が落ちる。

この失敗が厄介なのは、**見逃しが何も表示しない**こと。エラーも警告も出ず全部緑で通る。
運用していると誤検知だけが目につくので、直感に任せると必ず審査を緩める方向に流れる。
だから直感ではなく機械に守らせる。

## LM-008: 企画指示が無いと審査ごとスキップされていた

**症状**: `brief-gate.mjs` の冒頭に
`if (!spec.trim()) { console.log('gate skipped'); process.exit(0); }` があり、
指示なしで走る日次パイプラインでは審査が一度も動いていなかった。

**原因**: 「指示との整合を見る門」として作ったので、指示が無い＝見るものが無い、と考えた。
実際には具体性・ペルソナ・AI 特有表現・整合は、指示の有無と無関係に効く。

**回避策**: rubric の各項目に `requiresBrief` を持たせ、指示が無いときは
指示依存の項目だけを外して残りで審査する（重みは再正規化）。
設定チェックが「全項目が requiresBrief」の状態を禁止しているので、
将来この穴が再発すると `verify` が落ちる。

**一般化**: ゲートに `skip` の分岐を書くときは、それが fail-open かどうかを毎回疑うこと。

**何を落としたかだけ記録しても、見逃しは見つからない。何を通したかが要る。**

## LM-010: 審査役に総合点を出させると甘くなる

**症状**: 旧 `brief-gate.mjs` はモデルに `{"score": 0-100}` を出させ、その数字で合否を決めていた。
流暢な原稿には高い点が付きがちで、指示違反があっても 70 を超えることがあった。

**原因**: 採点者が自分の点数を申告する構造。加えて、指摘に根拠の引用を求めていなかったので、
当たり障りのない講評だけで通過できた。

**回避策**: モデルには項目ごとの観察だけを返させ、加重集計はコード側で行う（INV-013）。
減点には逐語引用を要求し、実在しない引用は破棄する（INV-014）。
致命的な項目は加重平均に参加させず veto にする。

**一般化**: LLM に判定させるときは「何を出させないか」のほうが効く。
最終判断の数字は、こちら側で計算する。

## LM-011: `biome check --write` を素直に走らせるとサイトが壊れる

**症状**: Biome が `src/pages/index.astro` の `import BaseLayout` を「未使用」と報告する。
`--write` を付けると **ページ全体を包むレイアウトの import が削除される**。
同様に `{age}` `{agentNova}` `{formattedDate}` `{sortedPosts}` など、
テンプレートから参照している frontmatter の変数が `_age` `_agentNova` … に
リネームされ、ページは「壊れていない顔で」undefined を描画する。

**原因**: Biome 2.x の Astro 対応は **frontmatter しか見ていない**。
`---` から下のテンプレートを解析しないので、テンプレートでしか使われていない
変数と import はすべて「未使用」に見える。

**回避策**: `biome.json` の `overrides` で `**/*.astro` に対して
`correctness/noUnusedVariables` と `correctness/noUnusedImports` を off にした。
astro ファイルの未使用チェックは `astro check` 側の責務。

**一般化**: リンタが「FIXABLE」と言っても、そのリンタがそのファイル形式を
本当に読めているかは別問題。自動修正を信じる前に、1 件を手で検証すること。

**同種の再発（2026-08）**: `--write` が `{ '貯金・節約': 0 }` の引用符を
`useLiteralKeys` として外し、`{ 貯金・節約: 0 }` にした。`・` は識別子に使えないので、
**次の `biome check` が自分の書いた行を parse error で弾く**（9件）。
日本語キーのオブジェクトを含むファイルに `--write` をかけたら、
その場で `biome check <file>` を読み直して parse error が出ていないか確かめること。

## LM-012: `.mjs` に TypeScript 構文を書いた 2 本のスクリプトは誰も実行できなかった

**症状**: `bun run analyze:themes` と `bun run gen:resume` が構文エラーで即死する。
`node --check` も通らない。package.json に登録され、README からも参照されているのに、
**一度も動いたことがない**。

**原因**: `.mjs` のまま型注釈 (`const x: T = ...`) と `import { type X }` を書いていた。
Bun は拡張子を尊重するので `.mjs` では型を剥がさない — 「Bun なら通る」は誤り。
`.mjs` は tsc の対象外でもあるため、型チェックにもかからず誰も気づけない。

**回避策**: 両方を `.ts` にリネームし、package.json の呼び出しも合わせた。
`analyze-themes` にはさらに 2 つの欠陥が隠れていた:
`ROOT_DIR` が `path.join(__dirname, '..', '..')` でリポジトリの外を指しており
（他のスクリプトはすべて `'..'` 1 つ）、型注釈も配列の `[]` が落ちていた。

**一般化**: **拡張子は型チェックの入口**。`.mjs` に型を書いた時点で、
その型は誰にも検査されない。型を書きたくなったら拡張子を変えること。

## LM-013: 継続性台帳が CI でコミットされず、正典が数週間前で凍っていた

**症状**: `data/continuity-ledger.json` の `updated` が 2026-07-28、
`diaryArticleCount` が 135 のまま。実際の記事は 172 本あり、
その間に書かれた到達点（積立5年目など）は台帳に一切入っていなかった。

**原因**: 2つが噛み合っていた。

1. `auto-post.mjs` は「台帳ファイルがあり schema が一致すれば、そのまま使う」
   実装だった。作り直すのはスキーマが変わったときだけ。
2. `daily-post.yml` の commit ステップが `src/content/posts/*.md` と
   `docs/agent-runs/` しか `git add` していなかった。Mira（VE-008）が更新した
   台帳は、ランナーが片付けられた時点で消えていた。

片方だけなら気づけた。両方揃うと、**毎晩正しく更新して、毎晩捨てて、翌朝
「キャッシュがあるから」と古いものを読み直す**という完全な循環になり、
ログには `✅ Loaded cached ledger` としか出ない。

**回避策**: 台帳は毎回 `src/content/posts` から作り直す（導出できるものは
導出する）。あわせて workflow の `git add` に `data/continuity-ledger.json` と
`data/trend-radar.json` を足した。走査は 170 本強のローカルファイルで、
LLM もネットワークも要らない — 更新漏れを心配するより安い。

## LM-014: 台帳が逆行記事を追認していた

**症状**: 台帳の `milestones` に「貯金300万達成！（2026-06-15）」の**後ろの日付で**
「貯金200万達成！（2026-06-28）」が並んでいた。次の書き手はこれを読んで
「200万を達成したばかり」という前提で書く。逆行が自己増殖する形になっていた。

**原因**: 金額の正典（`facts`）は最高到達点を守っていたが、`milestones` は
無条件に追記していた。逆行した記事が1本出てしまうと、その記述が出来事として
記録され、以後ずっとブリーフに載り続ける。

**回避策**: `isRegressiveMilestone()` で、到達済みの水準を下回る「達成」は
記録しない。あわせて回想の文（「以前、300万円を超えた時のことを…」）も
出来事から外す — 出来事への言及であって、出来事ではない。

**教訓**: 逆行を防ぐ層が2つ（正典・出来事）あるとき、**片方だけを守ると
もう片方が抜け道になる**。同じ判定関数を両方に通すこと。

## LM-015: 書き手が 2 つに増えた瞬間、同じログの末尾で必ず衝突する

**症状**: `linear-write.yml` が作った PR #223 が、`docs/agent-runs/2026-08.md` と
`data/continuity-ledger.json` で main と衝突した。

**原因**: 追記する書き手が 2 つになった。

| ワークフロー | いつ | 何を書くか |
|---|---|---|
| `daily-post.yml` | 11:30 UTC | 記事 + 実行ログ + 台帳 |
| `linear-write.yml` | 21:00 UTC | 記事 + 実行ログ + 台帳 |

両者が別ブランチで走ると、**どちらも月次ログの末尾に append する**ので、
内容が競合していなくても必ず「同じ行の後ろに両方が足した」衝突になる。

`linear-write.yml` は 2026-08 まで YAML が壊れていて一度も動いていなかった
（LM-012 と同じ commit で修復した）。**壊れていたおかげで衝突が起きていなかった**
だけで、直した瞬間に構造的な競合が表に出た。

**回避策**: `.gitattributes` で追記専用ログに `merge=union` を付けた。
両方の追記がそのまま残り、この 2 ファイルの衝突は原理的に消える。

```
docs/agent-runs/*.md  merge=union
docs/gate-runs/*.md   merge=union
```

**`data/continuity-ledger.json` には絶対に union を付けないこと。**
JSON なので構文が壊れるうえ、値は `pastArticles.length` から毎回導出される
（`scripts/auto-post.mjs`）。台帳の衝突は「古い側を捨てて作り直す」が正解で、
手で数字を合わせにいってはいけない。

**一般化**: 実際に PR #223 は `schema: 1 / count: 136`、main は Phase ν 後の
`schema: 2 / count: 173` だった。**そのままマージすれば台帳が逆行する** —
Phase ν が決定論的に止めようとしている、まさにその事故。
遅れて到着した自動生成 PR は、マージせず**作り直す**。

## LM-016: `git push` は「main が動かない」ことを前提にしていて、弾かれると記事ごと消える

**症状**: `daily-post.yml` の投稿ステップが `! [rejected] main -> main
(fetch first)` で落ちる。ジョブは赤く、その日の記事は**どこにも存在しない**。

**原因**: 押し方が

```
git commit -m "New post: …" && git push
```

だった。この 1 行は「push する瞬間の main は、checkout した瞬間の main と
同じだ」と仮定している。記事の生成には数分かかり、その間に PR が 1 本でも
マージされれば main は進む。進んでいれば non-fast-forward で弾かれる。

弾かれて失うのは push だけではない。**書き上がった記事そのもの**が消える:

- コミットはランナーのディスクにしか無く、ランナーは使い捨て
- 再試行は無い（`schedule:` は次の日まで来ない）
- 翌日の実行は翌日の日付で新しい記事を書く。消えた分を書き直す者はいない

LM-015 は「PR がマージできない」話だったが、これは「main へ直接押す側」の
同じ問題で、**失敗の代償はこちらのほうが高い**（PR は残るが、これは残らない）。

**回避策**: `scripts/push-with-rebase.sh` を通す。弾かれたら fetch →
rebase → 押し直しを、指数バックオフで数回繰り返す。追記専用ログは
`.gitattributes` の `merge=union` が自動で結合するので（LM-015）、衝突が
残るのは JSON の 3 ファイルだけ:

| ファイル | 解決 | 理由 |
|---|---|---|
| `data/continuity-ledger.json` | 今回の版を採る | 記事から毎回導出される。次回の実行が作り直す |
| `data/trend-radar.json` | 今回の版を採る | その日のスナップショット。古い側に価値が無い |
| `data/video-briefs.json` | 両側を union | 追記専用の台帳。片側を捨てると Issue が二重に生える |

**方針を持たないファイルが衝突したら、解決せずに落とす。** 推測で片側を
捨てるくらいなら赤いジョブのほうが安い。

**rebase 中の `--ours` / `--theirs` は直感と逆**であることに注意する:

```
--ours   = rebase の土台 = origin/main（他人が押したもの）
--theirs = いま replay しているコミット = この実行が書いたもの
```

導出物で「今回の版」を残したいときに選ぶのは `--theirs` のほう。

**一般化**: 自動化が書いたものを共有ブランチへ直接押すなら、**押し直しまでが
「書く」という仕事の範囲**。retry の無い push は、再現できない成果物を
コインの表裏に賭けているのと同じ。
