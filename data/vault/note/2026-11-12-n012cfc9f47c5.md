# 【AI開発最前線考察】エージェント開発環境の次｜コードより先に「正解の判定器」を作る｜1日3万マージを支えた検証の設計

[[tag/AIエージェント]] [[tag/ClaudeCode]] [[tag/Codex]] [[tag/AI開発]] [[tag/ソフトウェア開発]] [[tag/AIコーディング]] [[tag/開発日誌]] [[tag/Git]] [[tag/開発環境]] [[tag/CI]] [[tag/自動テスト]] [[tag/形式検証]]

1日に3万件。

AIエージェントが書いたコードを、ひとつの会社がそれだけ取り込んでいるそうです。Anthropicは2026年5月には1日平均約2,500件だったマージが、9月には1日3万件を超えたと書いています。

最初は「すごいなあ」で終わりそうになりました。でも割り算をしたら、少し怖くなりました。

3秒に1回、正しいかどうかを決めている

1日は86,400秒です。86,400 ÷ 30,000 で、だいたい2.9秒。約3秒に1回、何かが本番のコードに入っている計算になります。

仮に、人が1件を5分でレビューするとします。30,000 × 5分 = 150,000分で、2,500時間です。1日8時間働く人に直すと、だいたい312人。毎日レビューだけをする人が312人いる計算です。

これは私が勝手に置いた5分という仮定から出した数字です。会社の公表値ではありません。でも桁の感覚としては、もう人間の目では追いつかないところに来ている気がします。

じゃあ、その3秒ごとの「これは正しい」を誰が決めているのか。私がいちばん気になったのはそこでした。

   これまで                         いま起きていること

 人がコードを書く  ← 遅い        エージェントが書く  ← 速い
        │                                 │
        ▼                                 ▼
 人がレビュー                     ??? が「正しい」と判定  ← ここが詰まる
        │                                 │
        ▼                                 ▼
     マージ                             マージ

要点
・書く速さはもう問題じゃなくなった
・詰まっているのは「正しいと判定する速さ」
・判定する人の数は、書く速さに比例して増やせない

2社は同じ問題を、反対の方向から解いた

Anthropicは、手元にリポジトリを丸ごと複製するというGitの前提を捨てました。CIだけで1日に約2,500万回のチェックアウトをしていて、素朴に取得すると1日600PBを超えるGitの通信量になる、と書いています。

ここで検算を一つ。600PB ÷ 2,500万回 = 1回あたり約24GBです。つまりリポジトリを丸ごと持ってくると、1回で24GBくらい運ぶことになります。それを1日2,500万回。運ぶのをやめる、という結論になるのは分かる気がします。

一方のOpenAIは、Gitを捨てませんでした。新しいバックエンドのPandoで、Gitとの互換性を保つことを明確に選んでいます。面白いのは、その理由づけです。実際には、利用者もエージェントも、気にしているのは一つのブランチの中での更新の順番だけだ、と主張しています。

つまり、リポジトリ全体で「どの更新が先か」を全員が合意する必要はない、ということです。ブランチごとに順番が決まれば足りる。この割り切りで、並行して書き込めるようになったんだと私は読みました。

どちらが正しいのかは、私には決められません。ただ、反対の意見がいちばん強い形で出ていることは書いておきたいです。サーバーに置く中央集権型のソース管理は新しくない、PerforceもSVNもGoogleのPiperもそうだった、Anthropicは発明したのではなくエージェントのために再発見したのだ、という指摘があります。しかもAnthropic自身が、Scionは一般用途でGitの代わりになるものではないとはっきり書いています。

私はこの反論に、かなり納得しています。たぶん、新しいのは配管の形ではないんですよね。新しいのは「配管を使う客の99%が人間じゃなくなった」ことのほうです。Anthropicは、ソース管理の利用者のほぼ全員がエージェントと自動ジョブだと書いています。

本当の発明は、コードの外にあった

私がいちばん「ここだ」と思ったのは、OpenAIの作り方でした。

PandoはRustで書かれ、10週間で作られています。中心の設計を1人のエンジニアがやり、実装はCodexのエージェントたちがやったそうです。

これだけ聞くと「AIが書いた、すごい」になりそうです。でも中身を読むと違いました。人間がやったのは、エージェントが自分で答え合わせできる場所を作ることでした。

チームはGitの適合テストを書いて、エージェントが自分の変更を本物のGitの挙動と照らし合わせられるようにしました。競合状態を見つけるためには、決定的シミュレーションテストも使っています。

適合テストというのは、言ってみれば「本物のGitならこう返す」という正解集です。正解が手元にあれば、エージェントは何百回失敗しても自分で直せます。人間に聞かなくていい。

決定的シミュレーションテストのほうは、もう少し深いです。並行して動くプログラムのバグは、タイミング次第で出たり出なかったりします。だから再現できない。そこで、スレッドの実行順やネットワークの遅れを、乱数の種から全部決まるようにしてしまいます。同じ種なら、同じ順番で、同じバグが必ず出る。つまり「たまたま起きた失敗」を「何度でも起こせる失敗」に変えるやり方です。

さらに、エージェントはLeanやTLA+で仕様を書き、GitとPandoの両方を継続的に攻撃して穴を探したとも伝えられています。TLA+は、並行システムの設計が矛盾していないかを機械に調べさせる言語です。

   人間が作ったもの              エージェントが作ったもの

 ┌───────────────────┐
 │ 正解集（適合テスト） │──┐
 ├───────────────────┤  │      ┌─────────────────┐
 │ 再現できる失敗の場   │──┼───▶ │  実装（Rustのコード） │
 │（決定的シミュレーション）│  │      └─────────────────┘
 ├───────────────────┤  │             ▲
 │ 設計の芯（1人）      │──┘             │ 失敗 → 自分で直す
 └───────────────────┘          （人間に聞かない）

要点
・人間が作ったのは「コード」ではなく「答え合わせの装置」
・装置があれば、エージェントは自力で何百回も直せる
・逆に装置がなければ、どんなに速いエージェントも人間待ちで止まる

「AIの開発環境を開発する」の、その次

いま、AIの開発環境を自分で作るのが流行っている気がします。私もtmuxとGitのworktreeで、複数のエージェントを並べて動かす仕組みを作りました。カードを実行すると、エージェントが起動する。失敗したら別のモデルに渡す。最後は人間が承認してマージ。

これ自体は、悪くないと今でも思っています。

でも2社の話を読んだあとだと、私の仕組みは「エージェントを動かす側」しか作っていなかったと気づきました。答え合わせは、最後の私の目に全部乗っています。

自分の数字で考えてみます。エージェントを4つ並べて、それぞれ20分に1件、変更を出すとします。8時間で4 × 24 = 96件です。1件5分で見るなら、480分、ちょうど8時間。つまり、エージェントを4つ動かした時点で、私の1日はレビューだけで埋まります。5つ目を足しても、速くはならないんです。

ここで、前から私が気にしていた「依存関係のいちばん長い経路」の話がつながりました。全体の速さを決めている一番遅い工程はどこか。私の場合、それは私でした。

だから、次に作るべきなのはエージェントの管理画面ではない気がしています。その手前です。

   いまの私の仕組み                 次に足したいもの

 カード（やりたいこと）          カード（やりたいこと）
        │                          ＋ 判定条件（何が通れば正解か）
        ▼                                  │
 エージェントが書く                        ▼
        │                         エージェントが書く
        ▼                                  │
 別のAIがレビュー                          ▼
        │                         判定器が機械的に採点
        ▼                           │            │
 私が全部見る  ← 詰まる          合格だけ          不合格
                                 私が見る         エージェントが自分で直す

カードを作る時点で「何が通れば正解か」を書く。書けないカードは、エージェントに渡さない。これだけで、私の目に届く件数はかなり減ると思います。

最前線を全部まとめると、たぶんこういう順番

調べたことを一つの絵にすると、私にはこう見えました。

1つ目の段階は、AIが人間の作業を手伝う段階。2つ目は、人間が複数のAIに仕事を配る段階。私の仕組みはここです。3つ目が、いま2社がいるところで、配管そのものをエージェントの速さに作り直す段階。

そして、その先がたぶんあります。コードより、仕様と判定器のほうが本体になる段階です。

判定器さえ残っていれば、コードは捨てて書き直せます。Pandoがまさにそうで、古いシステムの依存を引き継がないためにゼロからRustで書き直しています。昔なら、そんな書き直しは何年もかかる大仕事でした。いまは、正解集があれば10週間でやれてしまう。

だとすると、私の87件のリポジトリで守るべきものも、少し変わってきます。コードそのものより、「このリポジトリは何をすれば正しいのか」という判定条件のほうかもしれません。コードは消えても、判定条件が残っていれば、また作れるので。

まだ決着していないこと

ただ、ここで一つ、どうしても引っかかっています。

OpenAIの例では、仕様や攻撃役もエージェントが書いていました。じゃあ、その判定器が間違っていたら、誰が気づくのでしょう。

判定器が甘ければ、エージェントは甘い判定に合わせて最適化します。テストを通るだけのコードを書く。これは前から怖いと思っていたことと同じです。

一つの答えは「本物と比べる」ことだと思います。Pandoの適合テストが強かったのは、本物のGitという、すでに何十年も使われてきた正解があったからです。比べる相手がいる問題は、判定器が作りやすい。

でも、私が作りたいものの多くには、比べる本物がありません。記事の良し悪し、画像の出来、研究のアイデア。こういう正解がふわっとしたものでも、判定器は作れるのか。それとも、そこだけは最後まで人間が持つべきなのか。

私はまだ分かりません。たぶん、ここが次の数年でいちばん揉める場所なんじゃないかな、という気がしています。

手元に落とすなら

大きな話をしたので、最後は自分の机に戻します。

私のPCは実効メモリが5.8GBくらいで、ローカルで重いものは動きません。でも判定器は、重くなくていいんです。テストを回すだけなら、軽いノートでも動きます。

だから当面やることは3つにします。

1つ目。カードに「判定条件」の欄を足す。空欄のカードはエージェントに渡さない。

2つ目。失敗したときに、乱数の種と入力を全部残す。あとで同じ失敗をもう一度起こせるように。

3つ目。1日に自分がレビューした件数を数える。4件のエージェントで8時間が埋まるという計算が合っているのか、実際の数字で確かめたいです。

88個目のリポジトリは、たぶん作らないと思います。その代わり、87件それぞれに「何が通れば正しいか」を一行ずつ書くところから始めてみます。地味だけど、3秒に1回の判定を支えていたのも、結局はこの地味な一行だった気がするので。
