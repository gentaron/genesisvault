# AIエージェントの「やっていいこと」をプロンプトではなくコードで決める——ツール実行の直前に許可と拒否を判定し、監査記録まで残すオープンソース基盤の仕組みと限界

[[tag/AIエージェント]] [[tag/python]] [[tag/セキュリティ]] [[tag/AIガバナンス]] [[tag/オープンソース]] [[tag/開発環境]] [[tag/ツール紹介]] [[tag/エージェント基盤]]

「ポリシーを1件も読み込んでいない場合、既定の動作は allow（許可）です」

エージェントの暴走を止めるための道具の、公式の制約ドキュメントにこう書いてあった。私は画面を二度見した。設定を入れ忘れた人の手元では、この鍵は開きっぱなしになる。守るための道具が、初期状態では何も守らない。

正直に言うと、私はこの一文を見つけるまで、この道具をかなり素直に信用していた。

なぜ「注意書き」では止まらないのか

いま多くの人が、エージェントに強い権限を渡し始めている。ファイルを消す。社内のAPIを叩く。メールを送る。決済を通す。

そして、その手綱をどこで握っているかというと、たいていはプロンプトの中の一行だ。「本番環境には触らないこと」「削除の前に必ず確認すること」。

ここが問題だった。プロンプトは命令ではなく、お願いである。相手は確率で動く仕組みだから、99回守って100回目に破る、ということが原理的に起こる。しかも破ったかどうかは、破られたあとにしか分からない。

　　交通ルールを紙に書いて助手席から読み上げるようなものだ。運転手が聞いていれば守られる。聞いていなければ、何も起きない。紙にはブレーキがついていない。

私はこの問題を、長いあいだ「モデルが賢くなれば減る」種類のものだと思っていた。ここは自分の見立てが甘かったと思っている。減りはするが、ゼロにはならない。ゼロにならない以上、確率の外側に止める仕組みが要る。

どう解いたのか——判定をコードの側に移す

Microsoftが公開しているAgent Governance Toolkit（エージェント・ガバナンス・ツールキット）は、この前提そのものを動かしている。

やっていることは、言葉にすればひどく素朴だ。エージェントがツールを呼ぶ、その直前に割り込む。呼び出し名と引数を見て、あらかじめ書いておいた規則に照らし、許可か拒否かを決める。そして決めた内容を記録する。

つまり、「守ってねと頼む」のをやめて、「通さない」に変えたということ。判定するのはモデルではなく、普通のプログラムだ。同じ入力には同じ答えが返る。

最小の使い方は驚くほど短い。ポリシーの雛形を作り、実行前の判定を1回呼ぶだけでいい。

runtime = AgentControl.from_path("policies/manifest.yaml")
session = HostSession(runtime, agent_id="...", session_id="...")
evaluation = session.pre_tool_call(tool_name="delete_file", args={"path": "report.txt"})
print(evaluation.verdict)

規則はYAMLの定義ファイルと、Rego（規則を書くための小さな言語）のファイルで持つ。既存の枠組みに後付けする場合、公式の説明では2〜3行の追加で済むとされている。

私が面白いと思ったのは、権限の持たせ方だ。よくある役割ベースの権限管理（RBAC。人や機械に「管理者」「閲覧者」といった役職を割り当てる方式）を、この設計は正面から退けている。設計判断の記録にはこう書いてある。静的な役割だけでは、実行時のリスク、取り消しやすさ、信頼の減衰を表現できない、と。

代わりに置かれたのが4段の実行リングだ。素性の分からないエージェントは一番外側の砂場から始まり、信頼の点数、呼び出し回数の上限、その操作が取り消せるかどうかで段が決まる。例外的な場面だけ、一時的に内側へ上げる。

空港の保安検査に近い。全員が同じ扉から入るが、通れる先の深さが違う。そして深く入るほど、通った記録が細かく残る。

ただし同じ記録には、リングは役割モデルより粗いので、細かい権限は結局ポリシーと承認フローで補う必要がある、とも書かれている。設計者自身が、これは万能の置き換えではないと認めている。

動かすのに何が要るか

ここは具体的な数字で書いておきたい。

配布されているPythonパッケージは py3-none-any、つまりOSを選ばない純Python形式のホイールで配られている。WindowsでもmacOSでもLinuxでも、同じものが入る。導入は pip install "agent-governance-toolkit[full]" の一行。

必要なPythonの版は、配布メタデータ上は3.9以上。ただし公式の前提条件には3.10以上、クイックスタートには3.11以上と書かれていて、3か所で数字が揃っていない。安全側に倒すなら3.11以上を用意するのが無難だと私は思う。この食い違いを見つけたときは、正直ちょっと笑ってしまった。準備中の版らしい荒さだ。

GPUは不要。特別なメモリ量の指定もない。Pythonが普通に動く機械なら足りる。Dockerは必須ではなく、本番ではエージェントごとに別コンテナへ入れることを「推奨」しているだけだ。Azureの資格情報も任意で、なくても動く。

他の言語からも使える。TypeScriptはNode 18以上とnpm 9以上、.NETは8以上、Goは1.25以上、Rustは1.70以上。ただし全機能が揃っているのはPythonだけで、他はポリシー・識別子・監査という中核部分に限られる。

ライセンスはMIT。無料。公開は2026年4月2日で、パッケージの最新版は4.1.0（2026年6月11日）。星は6000台、フォークは1100ほど、本流のコミットは2400を超える。10の仕様に対して992件の適合テストが回っている。位置づけは「公開プレビュー」で、正式版までに互換性のない変更が入りうると明記されている。

速度も出ている。ポリシー判定そのものは99パーセンタイルで0.1ミリ秒未満。ただしこれは判定だけの数字だ。複数のエージェントが分散して動く構成では、暗号検証に1〜3ミリ秒、信頼度の参照に1ミリ秒未満、身元の握手に10〜50ミリ秒、ネットワークに1〜10ミリ秒が乗り、全体では5〜50ミリ秒になると自ら書いている。この落差を隠していないのは、私は好感を持った。

この道具が守らないもの

ここからが本題かもしれない。制約の一覧が、率直すぎるほど率直なのだ。

行為は見るが、中身は見ない。禁止されたツールの呼び出しは止まるが、許可されたツールに渡された文章が幻覚かどうかは判定しない。間接的なプロンプト注入も確実には捕まえられない。個々には許される操作が、並べると有害になる筋書きも見抜けない。

記録は「試みと判定」であって「結果」ではない。APIが200を返しても、中身が古いデータなら、記録の上では成功に見える。

判定する部品とエージェントは同じプロセスの中にいる。カーネルの層ではない。だから隔離は、コンテナやネットワーク側に別途任せることになる。

資格情報の扱いも弱い。作業の切れ目でAPIキーを失効させる仕組みはなく、必要のなくなった鍵をエージェントが持ち続ける。

割り込みも今はまだ透過的ではない。エージェントの側が明示的に判定を呼ばないと、素通りする。

そして細かいが効く話。SDKによって識別子の書式が揃っていない。TypeScript・Rust・Goは did:agentmesh: で始まり、Python・.NETは did:mesh: で始まる。言語をまたいだ瞬間、ポリシーの照合が外れる。

拒否された呼び出しにも料金は発生する。止めても、止めた分の請求は来る。

いちばん強い批判

この道具を「まやかしだ」と書いた批評がある。論点は明快で、私が読んだ中では最も鋭かった。

要点はこうだ。売り文句は「エージェントの実行時セキュリティ」「OWASPの10項目すべてに対応」だが、実体はアプリケーションの中間層にある行為の門番にすぎない。思考も、発言も、結果も見ていない。それを基盤的な防御であるかのように語るのは誇張だ、と。

さらに具体的な指摘がある。監査ログが、ツール呼び出しの引数を無加工のまま保存している。つまり、守るために作った記録の中に、個人情報や資格情報がそのまま溜まっていく可能性がある。安全のための装置が、新しい漏れ口になりうる。

この批評が面白いのは、最後に道具を捨てていないところだ。「行為に対するガバナンスの層」と正直に呼べば、有用で実在する。ただし、その周りに巻かれた物語よりはずっと小さい——そう締めている。

別の見方をすれば、この批判は道具ではなく看板に向いている。中身は限定的だが本物で、看板が大きすぎる。看板を小さくすれば、評価は逆転する。

そして公式の側も、実は同じことを認めている。制約の文書には、これは多層防御のうちの一層であって戦略全体ではない、とはっきり書かれている。誇張しているのは道具ではなく、それを紹介する言葉のほうなのかもしれない。

何のコストが消えるのか

business の側から見ると、この種の仕組みが引き受けるのは、人間の目視確認と、事故が起きたあとの追跡である。

いまエージェントに強い操作を許している現場では、誰かが実行前に見る運用になっていることが多い。その確認が、規則として書ける範囲だけ機械に移る。全部は移らない。移るのは「取り消せない操作かどうか」「この宛先は許されているか」といった、判断が一意に決まる部分だ。

もうひとつは証跡である。何を試み、何を通し、何を拒んだかが最初から残る。あとから作文する作業が消える。ただし前に書いたとおり、残るのは試みであって結果ではない。ここを取り違えると、証跡があるのに何も証明できない、という間抜けな状態になる。

向いているのは、エージェントに削除・送信・課金のような取り消しにくい操作をすでに触らせていて、Pythonが構成の中心にあり、説明責任を求められる立場の人だと思う。

向いていないのは、単独の補助として使っているだけの人。エージェントが読み込む文書やデータベースの側を管理したい人。プロンプト注入そのものを止めたい人。この道具はそこには届かない。

まだ決めていないこと

私はこの道具を、良いとも悪いとも決めきれていない。

「お願いから判定へ」という発想の転換は、正しい方向だと感じる。確率で動くものを、確率で御そうとしない。その割り切りは筋が通っている。

一方で、判定する側とされる側が同じプロセスにいる構造は、どこまでいっても内側からの保証だ。本当に守りたいなら、外側に出さないといけない。そしてその外側は、この道具の担当ではない。

いちばん引っかかっているのは、やはり最初の一文だ。ポリシーを読み込んでいなければ既定は許可。これは設計の思想というより、導入のしやすさとの取引に見える。厳しくすれば、入れた瞬間に何も動かなくなって、みんな外してしまう。だから通す。気持ちは分かる。分かるが、鍵の初期値が開錠であることの意味は、やはり重い。

たぶん私は、しばらく小さな範囲で試して、どこで邪魔になるかを見ることになると思う。邪魔にならない安全装置は、たいてい何も止めていない。止まったときに初めて、値打ちが分かるたぐいのものだから。
