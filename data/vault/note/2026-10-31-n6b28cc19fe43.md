# 量子コンパイラをPythonだけの世界に置きたくない。10万個の無駄を0.1秒で消したQiskit 2.6 C API

[[tag/プログラミング言語]] [[tag/未来技術]] [[tag/量子コンピューティング]] [[tag/コンパイラ]] [[tag/Qiskit]]

量子回路に混ぜた100,000個の無意味な回転を、GPUも量子コンピューターも使わず、Cの小さなプログラムが約0.10秒で消した。

使ったのはQiskit 2.6の新しいC APIだ。量子回路を作るだけではなく、回路を変換するコンパイラの中身まで、Cから組み立てられるようになった。

量子コンピューターの記事なのに、最初に出てくるのがC言語。

なんか地味じゃない？　私も最初はそう思った。

でも、よく考えると量子計算で実際に困るのは、量子ビットへ命令を送る直前なんだよね。

人間が書いた量子回路を、その機械が本当に実行できるゲートへ変える。離れた量子ビットをつなぐために命令を並べ替える。結果を変えない無駄な処理を消す。これを担当するのが量子コンパイラだ。

量子アルゴリズムが楽譜なら、コンパイラは、その日の楽器と演奏者に合わせて楽譜を書き直す係に近い。

しかも量子ハードウェアは、方式ごとに使える命令も接続の形も違う。同じ回路をそのまま持っていけば動く、という世界ではない。量子ビットが増えるほど、この書き直しがかなり重要になる。

これまでQiskitでは、こうした作業をPythonから扱うのが中心だった。中の高速な処理はRustで書かれていても、利用者がコンパイラの流れを組み替える入口は、かなりPython寄りだった。

Qiskit 2.6は、そこへCの入口を開いた。

新しいC APIでは、独自のコンパイラパスを定義できる。パスは、回路へ施す1回分の変換だ。不要なゲートを消す。回路を別の表現へ変える。特定のハードウェア向けに命令を置き換える。そういう処理を1つずつ作り、パス・マネージャーへ順番に差し込める。

私は公式実装をcloneして、配布されているQiskit 2.6のライブラリへCプログラムを接続した。

100量子ビットの回路を用意し、角度がほぼ0のRXゲートを100,000個入れた。RXゲートは量子ビットをX軸まわりに回転させる命令だけど、今回の角度は1e-20。計算上は書かれていても、ほとんど何もしていない。

その後ろに、消えてはいけない回転を1個だけ置いた。

コンパイラパスを通す前は100,001命令。通した後は1命令。

削除処理そのものは約100ミリ秒だった。プログラム全体でも約144ミリ秒。ピークメモリは約57MBに収まった。

これ、量子コンピューターが速く計算した数字ではない。量子コンピューターへ送る前の古典コンピューターが、回路を整理した結果だ。

でも私は、ここに妙な面白さを感じた。

未来の計算機を動かすための仕事が、うちの非力なPCでも余裕のある大きさで走る。量子ハードウェアを持っていなくても、コンパイラの新しい部品を作り、回路がどう変わるかまでは確かめられる。

世界最先端の量子技術が机まで来るとき、量子ビットそのものが届くとは限らない。量子ビットへ命令を届ける仕組みのほうが、先に個人へ開かれることがある。

今回の新しさは、単にPythonをCへ書き換えたことではない。

パス・マネージャーは、入力と出力にどのIRを使うか宣言する。IRは中間表現のことで、プログラムを変換している途中の姿だ。

たとえば最初は、人が書いた量子回路として持つ。次に、命令同士の依存関係を表すDAGへ変える。DAGは、どの処理が先で、どの処理が並行できるかを矢印で表した形だ。最後はハードウェア固有の命令へ落としていく。

新しいAPIでは、パスが受け取るIRと返すIRを登録し、パス同士を接続するときに型を確認する。回路を受け取るはずの処理へ、別の内部表現を間違って渡す事故を、実行の流れを作る段階で止められる。公式も、複数のIRを通る変換を型付きのパイプラインとして扱えることを今回の中心に置いている。

私はここが、量子の話を超えて面白いと思った。

コンパイラって、1つの巨大な関数ではない。形の違うデータを、何段階も受け渡す工場みたいなものだ。その途中で「今ここにあるものは何なのか」が曖昧になると、変換は動いても意味が壊れる。

量子回路では、その壊れ方を簡単に目で確認できない。

普通のプログラムなら、結果が違えばテストで気づけることも多い。でも量子回路では、ゲートの並びを変えても同じ確率分布になる場合があるし、逆に似た見た目でも位相が変わって答えを壊すことがある。

だから、変換の各段階へ型を持たせる意味が大きい。

C APIの中では、vtableという仕組みも使われている。自分のパスがどの関数を持つか、どのIRを扱うかを関数ポインタの表として登録する。CにはPythonのクラスのような仕組みがないので、振る舞いを表にして渡している。

見た目は少し無骨。でも、そのおかげでC以外の言語も接続しやすい。

CのABIは、言語同士が接続するときの共通端子として広く使われている。C++やJulia、Fortran、Rustなどからも呼びやすい。Qiskitの中心が「Pythonのライブラリ」から「Pythonからも呼べる量子コンパイラ基盤」へ、少しずつ形を変えているように見える。

量子回路を保存するQPYもC APIへ降りてきた。

QPYは、量子回路を持ち運ぶためのバイナリ形式だ。Qiskit 2.6ではCから回路を書き出し、あとでPythonから読み直せる。反対方向も通る。新しいQPY v18では、大きなレジスタを持つ回路の保存形式も小さくなった。

私は1,000命令を持つ回路を1,000個作り、CだけでQPYのメモリ領域へ保存して読み戻してみた。

できたデータは約43MB。書き出しは実行ごとに少し揺れたけれど0.2秒から0.5秒ほどで、読み戻しは約2秒だった。1,000回路とも戻り、各回路の命令数も保たれた。

ピークメモリは約725MBまで増えた。

最初の57MBという数字だけを見て「量子コンパイラはいつでも超軽量」とは言えないんだよね。処理する回路を1,000個抱えれば、データのぶんだけメモリは増える。

それでも、GPUは使っていない。量子ハードウェアも使っていない。料金も0円だった。

ここまでなら、個人でも量子コンパイラの挙動をかなり具体的に触れる。

ただし、「QiskitからPythonが消えた」と書くのはまだ早い。

今回のCプログラムはPythonインタプリタを起動していない。処理もC APIからRustの中身へ直接入っている。

それでもQiskit 2.6の共有ライブラリは、リンクするときにlibpythonのシンボルを要求する。内部データの一部が、まだPythonの型と結びついているからだ。公式資料も、インタプリタは使わないがPythonライブラリは現在も必要で、完全に外す作業は次の版へ続くと説明している。

実際、私はここで1回止まった。

Pythonライブラリへの通常のリンクが壊れていて、明示的に実体のファイルを指定し直す必要があった。Cのプログラムを書けたからといって、きれいな単体バイナリがぽんと完成したわけではない。

ソースから全部ビルドする場合は、C11対応コンパイラに加え、Rust 1.89とcbindgenも必要になる。うちの非力なPCで試すなら、コンパイル済みの配布物を利用するほうが現実的だと思う。

C API自体も、まだ実験的と明記されている。小さな版更新でも形が変わる可能性がある。Pythonで作った回路をC側のトランスパイラへ無理に渡すと、C APIへ公開されていない構造が欠け、完全な結果にならない場合もある。

なので、今日から量子アプリを全部Cで書き直そう、という話ではない。

Pythonは実験や可視化がしやすいし、量子アルゴリズムを試す入口として今も強い。Cでメモリ管理や所有権を間違えれば、量子回路以前のところで普通に壊れる。

今回のパス・マネージャーも、入力した回路の所有権を受け取る。処理後に元のポインタをもう一度解放すると危ない。未来の技術へ近づいたのに、悩みはかなり古典的だ。ちょっとかわいいけど、油断はできない。

それでも、このC APIは量子計算の置き場所を変えるかもしれない。

高性能計算の世界では、シミュレーション本体がC++やFortranで動き、そこから量子処理を呼びたい場面がある。今まではPythonを間に立てたり、回路形式を独自に変換したりする必要があった。

Cの共通端子があれば、古典計算の途中から量子回路を作り、コンパイルし、QPYとして次の処理へ渡せる。

個人開発でも、量子回路を扱う別言語の小さな処理系を作りやすくなる。独自の言語からQiskitのPython構文を生成するのではなく、C ABIへ直接つなげばいい。

次に来そうなのは、量子コンパイラのプラグインがPythonパッケージではなく、共有ライブラリとして配られる流れだと思う。

ハードウェアの開発元が、自分たちのネイティブゲートへ変換するパスを公開する。別の言語で書いた回路も、同じ型付きパイプラインへ入る。量子コンパイラが1つのアプリではなく、言語をまたぐ実行基盤へ近づく。

もう1つは、QPYのような中間形式が、量子計算の本当の境界になること。

回路を作る言語と、回路を最適化する言語と、量子ハードウェアへ送る仕組みが、同じ言語である必要はなくなる。Python対Cという勝ち負けではなく、得意な場所だけを担当して、形式で受け渡す形だ。

量子コンピューターが家庭へ置かれたわけではない。10万個の命令を消せても、量子計算の結果は1つも得ていない。

でも、未来の量子機械へ命令を届けるコンパイラは、約57MBのプロセスとして普通のCPUで動いた。

私はこういう降り方が好きなんだよね。

派手な量子ビット数が増える前に、言語と機械の間にあった壁が1枚だけ薄くなる。まだPythonライブラリという細い糸は残っている。でも、その糸がどこにあるのかまで見えるようになった。

たぶん次は、その糸が本当に切れたとき、また試したくなる。
