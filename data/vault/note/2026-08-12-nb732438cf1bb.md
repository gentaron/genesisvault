# 【witr】「このプロセス、誰が動かしてるの？」に一発で答えてくれるコマンドラインツール【解説】

[[tag/ツール]] [[tag/windows]] [[tag/Git]] [[tag/witr]] [[tag/リポジトリツール]]

サーバーの調子が悪いとき、私が一番困るのは「何が動いているか」ではなく「なぜそれが動いているか」が分からない瞬間です。

ps を叩けば、動いているプログラムの一覧は出てきます。lsof を使えば、3000番のポートを誰が握っているかも分かります。それでも、そこから先が続かない。目の前にいる node というプロセスが、いったい誰の指示で立ち上がって、誰が生かし続けているのか。そこを知るには、いくつものコマンドを行ったり来たりして、頭の中で線をつなぎ直す作業が必要でした。

　　地面に落ちている一本の糸を見つけたのに、それがどこから伸びてきたのか分からない。糸をたぐるための道具がなくて、しゃがんだまま考え込んでいる。私の感覚はいつもそれに近いものでした。

その「たぐる」部分だけを引き受けてくれるツールが、8月9日にGitHubのトレンド1位になっていました。witr（ウィター）といいます。名前は "Why Is This Running?" の頭文字で、そのまま「これはなぜ動いているのか」という意味です。私はこの名前の付け方がまず好きになりました。

witrは結局、何をしてくれるツールなのか

一言でいうと、プロセスの家系図を自動で描いてくれるツールです。

コンピューターの中で動いているプログラムのことを「プロセス」と呼びます。プロセスには必ず親がいます。あなたが手で python app.py と打ったなら親はあなたのターミナルですし、サーバーが自動で起動したものなら、親はOSの管理役です。この親子関係は延々とさかのぼることができて、最後は必ずOSの一番最初のプロセスに行き着きます。

witrは、その最後までの道のりを1本の線として表示してくれます。

従来のやり方：「何が動いているか」までしか分からない

  ps aux        → node (pid 1482060) が動いている
  lsof -i :5000 → 5000番ポートを握っているのも node らしい
  systemctl     → 該当するサービスは見当たらない……
                  （で、結局これは誰が起動したの？）

witr のやり方：「なぜ動いているか」を1本につなぐ

  systemd (pid 1)
      └─ PM2 v5.3.1 (pid 1481580)
            └─ python (pid 1482060)   ← 探していたのはこれ

上の図で言えば、「OSの起動役（systemd）が PM2 という常駐管理ツールを立ち上げ、その PM2 が python を動かし続けている」という事情が、一目で分かります。ここまで分かれば、止めたいときにどこを止めればいいかも決まります。pythonだけ殺しても PM2 がまた立ち上げてしまう、という徒労を踏まずに済むわけです。

　　症状だけを見て薬を出すのと、原因まで確かめてから手当てするのと。急いでいるときほど前者を選びたくなりますが、あとで痛い目を見るのもだいたい前者でした。

入り口が「プロセス名」だけではない、というのが良いところ

私が実際に触ってみて一番ありがたかったのは、調べ始める入り口が複数用意されていることでした。

名前で調べたいなら、そのまま名前を書きます。

witr node

「ポート番号しか分からない」という状況もよくあります。3000番が埋まっていて開発サーバーが起動しない、というあの場面です。

witr --port 3000

プロセスID（プロセスに割り振られる番号。psコマンドなどで表示される「pid」のことです）が分かっているなら、それでも構いません。

witr --pid 10688

さらに、ファイルを掴んでいる犯人を探すこともできます。削除できないファイルがあるとき、それを開きっぱなしにしているプロセスを名指ししてくれる、という使い方です。

そして面白いのが、これらを混ぜられること。

witr nginx --port 5432 --pid 1234

名前・ポート・プロセスIDを一度に投げると、それぞれの結果が順番に並びます。調査中は思いつく手がかりを片っ端から試したくなるものなので、この「混ぜていい」という設計は素直に助かりました。

　　鍵束を持って建物を回るとき、どの鍵がどの扉か覚えていなくてもいい。とりあえず全部持っていけば、開く扉から開いていく。そういう気楽さがあります。

出力に「文脈」が付いてくる

witrの出力は、ただの親子関係だけでは終わりません。以下のような情報が一緒に並びます。

プロセス本体の情報として、実行ファイル、プロセスID、実行しているユーザー、コマンド全文、起動時刻、そして再起動された回数。再起動回数が出るのは地味に効きます。「さっきから何度も落ちて立ち上がり直している」という事実が数字で見えるからです。

なぜ存在するのかという欄には、先ほどの家系図が入ります。

発生源の欄には、systemd（Linuxの起動・常駐管理役）、launchd（macOSの同じ役割）、docker、SSH接続、cron（定時実行の仕組み）、あるいは単にシェルから手で叩いた、といった「元締め」が書かれます。

文脈の欄には、作業ディレクトリ、Gitのリポジトリ名とブランチ名、コンテナの情報、そしてポートを外向きに開いているかどうか。Gitのブランチ名まで出るのは、開発中に同じようなプロセスをいくつも立ち上げてしまう人には嬉しいところだと思います。どのブランチで動かしていたやつなのか、それだけで判別がつきます。

警告の欄も用意されています。root（管理者権限）で動いている、危険な権限を持っている、外部から見えるアドレスにポートを開いている、メモリ使用量が異常に多い、稼働時間が長すぎる、実行ファイルがすでに削除されている——このあたりを自動で拾って知らせてくれます。最後の「実行ファイルが削除済み」は、私が自力で気づける自信のない項目でした。

ターミナルの中に、小さなダッシュボードが立ち上がる

引数を何も付けずに witr とだけ打つか、-i を付けると、対話モード（TUI）に入ります。TUIというのは、ターミナルの文字だけで作られた画面のことです。マウスも効きます。

そこには、リアルタイムで更新されるプロセス一覧、開いているポートの一覧、選んだプロセスの詳細（家系図、子プロセス、環境変数、作業ディレクトリ）が並びます。さらに、選んだプロセスに対して停止・終了・一時停止・再開といった操作を直接送ることもできます。優先度の変更もできます。

ただ、私が触っていて感じたのは、このモードの本当の価値は「操作できること」ではなく「眺められること」のほうかもしれない、ということでした。何か問題が起きてから調べるのではなく、平常時にぼんやり眺めておくと、いざというときに「いつもと違う」に気づける。そういう使い方が向いている気がします。

　　毎朝同じ道を通っていると、ある日ふと、いつもある看板がないことに気づく。異常を見つけるための一番安上がりな方法は、正常をよく見ておくことだと思っています。

導入は、たぶん想像より簡単です

witrはGo言語で書かれていて、配布形態は単体で動く実行ファイル1つです。つまり、事前に何かをインストールしておく必要がありません。

Linux、macOS、FreeBSDなら、以下の1行で入ります。

curl -fsSL https://raw.githubusercontent.com/pranshuparmar/witr/main/install.sh | bash

Windowsの場合はPowerShellで以下です。

irm https://raw.githubusercontent.com/pranshuparmar/witr/main/install.ps1 | iex

もっとも、私はネットから取ってきたスクリプトをそのまま流すのが少し苦手なので、パッケージ管理ツール経由をおすすめしたいところです。20以上の配布経路が用意されています。

Homebrewなら brew install witr、Windows標準のWingetなら winget install -e --id PranshuParmar.witr、Arch Linuxなら yay -S witr-bin、Node.jsのnpmでも npm install -g @pranshuparmar/witr で入ります。Chocolatey、Scoop、Conda、FreeBSDのpkgにも対応しています。Go言語の環境がある人なら go install github.com/pranshuparmar/witr/cmd/witr@latest でも構いません。

ライセンスはApache 2.0で、商用利用も含めて幅広く使えます。

知っておいたほうがいい制約

良いところばかり書くのは誠実ではないので、引っかかりそうな点も並べておきます。

まず権限です。すべてのプロセスの詳細を見るには、管理者権限が要る場面があります。Linux・macOS・FreeBSDなら sudo witr、Windowsなら管理者としてターミナルを起動する、という形です。特にmacOSは、システム保護の仕組み（SIP）によって、管理者権限があっても一部のシステムプロセスは覗けません。ここは仕様として受け入れるしかない部分だと思います。

次にプラットフォームごとの差です。基本の「名前・プロセスID・ポートから調べる」機能はすべてのOSで動きますが、それ以外は揃っていません。ファイルから逆引きする機能はWindowsで使えません。環境変数の表示はmacOSで部分的、Windowsでは使えません。SSHやtmux（1つの画面を分割して使うツール）の検出、そして定時実行の検出も、Windowsでは動きません。TUIからのプロセス操作もWindowsは対象外です。Windowsで使う場合は「基本機能は動くが、細かい文脈情報は諦める」くらいに構えておくのが良さそうです。

最後に、作者自身がやらないと宣言していることにも触れておきます。witrは監視ツールの代わりにはならず、性能を細かく測るプロファイラでもなく、systemdやdockerのコマンドを置き換えるものでもなく、問題を自動で直してくれるわけでもありません。あくまで「読むだけの、原因を明らかにするための道具」だと位置づけられています。

私はこの割り切りが好きです。何でもできると謳うツールより、できることの輪郭がはっきりしているツールのほうが、結果的に長く使える気がしています。

　　万能ナイフを1本持つより、よく切れる包丁を1本持つほうがいい。少なくとも私は、そちらのほうが料理が続きました。

実行結果を機械に渡したいときは

--json を付ければ、結果がJSON形式で出てきます。プログラムから扱いやすい形式です。

さらに、終了コード（コマンドが終わったときに返す数字。スクリプトの中で条件分岐に使えます）が意味のある形で設計されています。0なら「見つかった、警告なし」、1なら「見つかったが警告あり」、2なら「見つからなかった」、3なら「権限が足りない」、4なら「入力が不正、あるいは候補が多すぎて絞れない」。

この設計のおかげで、定期チェックのスクリプトに組み込むといった使い方もできそうです。たとえば「特定のポートを誰かが外向きに開いていたら通知する」といった監視を、数行で書けることになります。

　　道具そのものより、道具を他の道具につなげる穴が空いているかどうか。私はそこを見て、長く付き合えるかを判断することが多いです。

私がこのツールに惹かれた理由

正直に言えば、witrができることの大半は、既存のコマンドを組み合わせれば実現できます。新しい原理が発明されたわけではありません。

それでも私がこれを面白いと思ったのは、「なぜ」を主語にしたことそのものにあります。

長いあいだ、システムを調べる道具は「何が」「どれくらい」を答えるものでした。何が動いているか、どれくらいメモリを使っているか、どれくらいの通信量か。数えられるものを数える方向に進化してきたと思います。

witrが選んだのは、そこから一歩ずれた場所です。数えるのではなく、つなぐ。バラバラに存在していた事実のあいだに、因果の線を引き直す。やっていることは既存の情報の再編集にすぎないのですが、その再編集こそが、私たちが頭の中で毎回やらされていた面倒な作業でした。

　　同じ材料を並べ替えるだけで、意味が立ち上がることがある。散らばった写真を時系列に並べた瞬間に、それが物語に変わるように。

21000を超える星が付いているのは、たぶん多くの人が同じ面倒を抱えていたからだと思います。新しい機能が欲しかったのではなく、既にある情報を、人間が読める形に整えてほしかった。

そう考えると、これから作られるべき道具は、まだ結構たくさん残っているのかもしれません。私たちが「いつもの手順」として無意識に繰り返している作業のなかに、witrと同じ種類の空白が眠っている気がしています。

自分の作業ログをしばらく眺めてみると、案外そういう空白が見つかるのではないでしょうか。私も今週は少し、そういう目で自分の手順を見返してみようと思っています。
