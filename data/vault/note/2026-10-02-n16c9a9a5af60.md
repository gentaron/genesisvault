# 【学習しない】NVIDIA Kumo Tabular｜表データの予測から学習そのものを消した28Mのモデル｜GPUなし1コアで1000行2.2秒、調整の22.8秒が消える

[[tag/機械学習]] [[tag/nvidia]] [[tag/ローカルAI]] [[tag/表データ]] [[tag/GPUなし]]

エクセルみたいな表を1枚渡すと、学習を1回もせずに次の行を予測してくれるモデルが、9月の終わりに重みごと公開された。しかも商用利用まで無料のライセンスで。

これ、地味に見えてけっこう大事だと思う。表の予測ってこれまで、勾配ブースティング（決定木をたくさん重ねるやつ）を回して、木の深さだの学習率だのを総当たりで探す作業だった。その探す部分がまるごと消える。私の非力なマシンでも、1000行くらいの表なら2.2秒で答えが返ってきた。

名前は Kumo Tabular。作ったのは NVIDIA で、コードは structured-data-models という名前のライブラリとして GitHub に Apache 2.0 で置いてある。pip でそのまま入る。重みは Hugging Face の nvidia/Kumo-Tabular にあって、ソースを読むと v1.0.0 というタグを取りに行く作りになってた。サイズは小・中・大の3つ。

で、何をやってるのか。ふつうの機械学習は「データで重みを当てはめる」んだけど、こっちは重みを一切いじらない。正解がついてる行を文脈として全部そのまま読ませて、1回の前向き計算で未知の行の答えを出す。文脈内学習、つまり例を見せるだけで覚えさせるあれを、文章じゃなく表でやってる。

いちばん面白いのは、何を捨てたか。行と行を全部つきあわせる注意（どの行がどの行と似てるかを総当たりで見るやつ）を捨てて、代わりに128個の「代表点」を置いた。全部の行をいったんこの128個に要約して、そこ経由でしか見ない。ソースのコメントに計算量が書いてあって、総当たりなら行数のかけ算になるところを、行数の足し算に落としてる。狭い通り道をわざと作って、そこを通らせてるイメージ。

ここ、自分で測ってみた。1コア、GPUなし。1024行だと2.08秒。それを2048行に倍やすと5.12秒。4096行で15秒、8192行で37.7秒。倍にするたびに2.5倍から3倍。代表点のおかげで完全な二乗にはなってないけど、きれいな比例にもなってない。最後に残る行どうしの計算が効いてる感じ。この伸び方のまま公表されてる上限の6万行までいくと、私の雑な外挿では10分くらい。これは測った数字じゃなくて延長線の話。

それより実用的だったのがもう一方。訓練行を1回読ませたあと、その読んだ結果を使い回す仕組みがある。1024行を読み込ませるのに2.5秒かかって、そのあと新しい行を500行まとめて判定したら0.83秒。1行あたり1.65ミリ秒。つまり重いのは最初に表を読むところだけで、あとは1行2ミリ秒。この構造は普通のPCにかなり優しい。

比較のために、同じ形のデータで勾配ブースティングも回した。何も調整しないと0.25秒で正解率93.0%。そこから36通りの設定を3分割で総当たりすると22.8秒かけて94.0%。22.8秒払って1ポイント。Kumo のほうは調整という概念がないので、2.2秒の1回で終わる。ここが「できなかったことができるようになる」の芯だと思う。精度で勝つ話じゃなくて、調整できる人しかやれなかったことが、調整しない人にも渡される話。

で、崖もちゃんとある。分類のクラス数を変えて測ってたら、10クラスまでは2.2秒なのに、11クラスにした瞬間26.2秒になった。12倍。何これと思ってソースを見たら、このモデルは一度に10クラスまでしか見られなくて、それを超えると誤り訂正符号（クラスを符号に割り振って何回も分けて解くやつ）に切り替わる。だから回数が増えて遅くなる。捨てたものが数字になって出てくる瞬間って気持ちいい。

しかもその符号の実装、サードパーティのライセンス表記を読むと Prior Labs のコードから派生してると書いてある。Prior Labs は TabPFN という、この分野でずっと先に走ってた会社。つまり NVIDIA のモデルは、ライバルの道具箱から一部借りてる。ついでにこのライブラリ、Google の TabFM も、学会発表のモデルも、同じ入口で呼べるように同梱されてる。自分の土俵を自分で作って、そこに自分のも並べた、みたいな。

その TabPFN の最新版と並べると、分かれ目が一点だけはっきりする。TabPFN 3.5 は100万行まで食べられて、文字列も時間も画像も扱える。Kumo は6万行、100列、10クラスまで。性能表だけ見たら前者が広い。でも TabPFN の公開重みは研究用途だけで、仕事で使うには別契約が要る。Kumo は商用可。だから6万行より下の表を仕事で扱う人にとっては、広さじゃなくてライセンスのほうが先に効く。

ベンチの順位はどっちも1位を主張してて、Elo は1950対1910。ただどっちも自社で走らせた数字で、ベンチの管理側はまだ再現してないらしい。ここは決めずに置いておく。

正直に書いておくと、私は中身の賢さを確かめていない。うちの環境から公開重みが引っぱってこられなくて、構造だけ組んで速さと大きさを測った。ランダムな重みのままだと正解率はちょうど50%、つまりコイン投げ。測ったのは値段のほうだけ。パラメータ数は自分で数えて、小さいのが2850万、大きいのが2億1570万。公表の28Mと215Mに合う。中くらいだけ6250万で、71Mと書いてる記事と合わなかった。調べたら71という数字は学習に使った合成テーブルの枚数のほうだった。たぶん取り違え。

あと、このモデルは実在するデータを1枚も見てない。全部、因果の構造から機械が作った人工のテーブルで学んでる。そしてその生成器と手順は公開されてない。だから外の人が同じものを作り直すのは今のところ無理。すごい話とこわい話が同時に置いてある感じ。6万行を超えた表は行をランダムに間引いてアンサンブルするし、列が多すぎれば列も間引く。回帰では1つの数を出すのをやめて、999個の目盛り（どのあたりに来そうかの分布）を返す。捨て方が全部あけっぴろげ。

これがここまで来たなら、次は表計算ソフトの中に入ってくると思う。Google のほうはもう SQL から呼べるようにしてあるし。あとは仕様表に「何行まで」が精度と並んで載るようになる気がする。

壊れた入力も入れてみた。文字の列を混ぜても、半分が空っぽの列を混ぜても、1行しかなくても、200列あっても、落ちずに最後まで走った。数値しか食べないと書いてあるのに通ったのは、前処理が勝手に数値に直してるから。200列は10秒から24秒に伸びたので、通るけど遅い。黙って遅くなるタイプは、気づかないと地味に危ない。

うちのは非力だから、小さいサイズを4096行くらいまでで使うのが現実的かな。それでもメモリは2GBちょっと使ってたし、15秒待った。6万行を数分で回せる人がうらやましい。でもいつか、ちゃんとしたマシンで、手元の表を全部これに食わせてみたい。
