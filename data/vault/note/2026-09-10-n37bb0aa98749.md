# 道具を増やしたら、エージェントは前にできたことを忘れるらしい

[[tag/生成AI]] [[tag/AIエージェント]] [[tag/LLM]] [[tag/mcp]] [[tag/AI研究]] [[tag/ハーネス]] [[tag/エージェント評価]] [[tag/EvoHarnessBench]]

きょう見つけたのは EvoHarnessBench っていう評価ハーネス。ハーネスっていうのは、モデルの外側にくっついてる実行環境のことね。

呼べる道具の一覧、手順書みたいなスキル、投げ先の子エージェント、そういうモデル本体じゃない部分ぜんぶ。

で、このベンチはそのハーネスをわざと段階的に太らせて、太らせる前にできてたタスクをもう一回やらせる。それだけ。それだけなんだけど、結果がけっこうこわい。

作ったのは Salesforce Research と UNC チャペルヒルとウィスコンシン大の合同チーム。arXiv に v1 が出たのが2026年9月3日で、まだ一週間しか経ってない。日本語で書いてる人、たぶんまだいない。

なんでこれを見つけて「うわ」ってなったかというと、わたし、道具は増やせば増やすほど強くなると思ってたから。

MCP サーバー足すとか、スキル一個書き足すとか、そういうの全部プラスだと信じてやってたんだよね。このベンチはそこを疑ってる。

中でやってることを具体的に。ハーネスを三つの軸で伸ばすの。呼べる道具、手順書のスキル、専門の子エージェント。全部で実行できる道具が520個、スキルが42本、子エージェントが62体ある。これを一気に全部見せるんじゃなくて、よく使われるものから順に、段階を分けて解禁していく。17本の流れがあって、それぞれ3段から6段。

タスクのほうは802問を1510例に展開してあって、各タスクは「解くのに必要な道具がぜんぶ揃った最初の段」に割り当てられる。つまり、ある段で初めて解けるようになった問題は、その後の段でもずっと解けてなきゃおかしいわけ。

測り方は継続学習から借りてきてる。後ろ向き転移と前向き転移、論文だと BWT と FWT って書いてあるやつ。

後ろ向きは「前の段で解けてた問題が、いま解けるか」。前向きは「新しく増えた道具を、ちゃんと使いこなせるか」。この二つを分けて見るのがこのベンチのいちばん大事なとこだと思う。

で、結果。前の段で解けてた問題が、崩れる。モデルの重みは一文字も変わってない。増えたのはカタログだけ。

なのに後ろ向き転移がマイナスになる。論文はこれをハーネス起因の忘却って呼んでる。

試されてるのは ReAct に GPT-5 を載せたやつ、Codex、Claude Code の Sonnet-4.6、あと AutoGen と DeLM っていうマルチエージェント。単発のエージェントは道具の軸で軒並みマイナスだった。

理屈としてはまあ分かる気はする。選択肢が増えれば、その中から正しい一個を引く確率は落ちる。説明文が似てる道具が混ざれば取り違える。カタログ自体が文脈を食う。

ぜんぶ当たり前の話。でも当たり前の話を、ちゃんと段を切って測った人がいままでいなかったのが、たぶんこの論文のいちばんの価値なんだと思う。わたしも薄々思ってはいたけど、測ろうとは一回も思わなかったし。

もう一個おもしろかったのが、直し方の綱引き。忘却を直すために既存の自己進化手法をいくつも当てるんだけど、後ろ向きを良くすると前向きが死ぬ。GEPA と Meta-Harness は後ろ向き転移をプラスに戻せたけど、そのかわり新しい道具への適応がマイナス28.5%とマイナス11.1%まで落ちた。過去を守ろうとすると新しいものを覚えなくなる、っていう。

人間かよ。

道具の軸だと MemToolAgent が正答率38.6%まで上げてて、素の30.2%よりは効いてるんだけど、スキルとエージェントの軸に持っていくと効き目がバラバラになる。ぜんぶ一律に効く直し方は、いまのところない。

スキルまわりの話がわたしはいちばん引っかかった。このベンチのスキルは「潜在スキル」って呼ばれてて、プロンプトに勝手に差し込まれない。エージェントが自分で取りに行かないと使えない。

そしたら素の GPT-5 は、用意されたスキルをほぼ一個も呼ばなかった。同じ問題で、タスク特化に仕込んだ GPT-5.5 は82%使った。つまりスキルを書いても、読みに行く癖のないモデルとハーネスの組み合わせだと、置いてあるだけで終わる。

わたし、スキル書いて満足してたことあるので、これはちょっと胸が痛い。

正直そんなにすごくないかも、と思ってるところも書いとくね。スキルとタスクの対応づけがキーワード一致のヒューリスティックで、そのスキルが本当に必要だったかは保証されてない。

著者たちも自分で書いてる。あと二つの環境で結果がかなり食い違ってて、片方で強い手法がもう片方で沈む。マルチエージェントは計算予算が足りなくて最後まで回せなかった実験があるって正直に書いてある。ベンチ全体を回すのにいくらかかるかの数字も出てない。

だからこれは「答え」じゃなくて、「ここに穴があるよ」って指差した論文。それはそれで十分だと思うけど。

コードは、探した範囲だとまとまった配布が見つからなくて、研究所のドメインに置かれた閲覧用のページがあるだけっぽい。同名のリポジトリはいくつかあるけど別人のやつ。ここは確かめきれてない。

で、うちの子の話。今回のは重みじゃないから、うちの非力なノートでも理屈のうえでは動くの。動くんだけど、1510例を複数の段ぶん、複数の手法ぶん回すってことは、それだけ API を叩くってこと。無料枠でやりくりしてるわたしがまるごと再現するのは無理。

これ絶対うちの子じゃ無理だ〜、というか予算が無理。ちゃんとしたマシンと予算がある人、うらやましい。

でも縮小版なら自分でもいけるなと思ってる。いま自分が使ってるエージェントの設定で、小さい課題を10個くらい決めて通過数を数えておく。そのあと MCP を一個足して、同じ10個をもう一回。

それだけで後ろ向き転移の真似事にはなる。モデルはクラウドにいるから、うちのが非力でも困らないのがこういうときはありがたい。落ちてたら落ちてたで、道具を足したのが原因かもって疑えるようになるだけで全然ちがう気がする。

いつかローカルで全部回せるマシンを手に入れたら、ちゃんとやりたい。

これが刺さったら次に来そうなの、ひとつ書いておくと、道具のカタログを痩せさせる道具だと思う。

いま「MCP を何十個つないだ」が自慢になってるけど、この論文の見方だと、それは自慢じゃなくてただの負債になりうる。だから次は、使ってない道具を自動で隠す仕組みとか、タスクに応じてカタログを絞り込むルーターみたいなものが出てくるんじゃないかな。

あと、ハーネスの更新に「回帰テスト通しました」って注記がつく日も来る気がする。ソフトウェアだと当たり前のことが、エージェントの世界ではまだ当たり前じゃないので。

まとめると、道具を足すのはタダじゃなかった、という話。わたしはこれからスキルを一本足すたびに、前できてたことが崩れてないか、ちょっとだけ疑ってから足すと思う。ちょっとよく分かんないんだけど、たぶんそれが正しい。
