# Graphifyの発想を自分のAI環境で試したら、コードの「つながり」が見えてきた

[[tag/AIエージェント]] [[tag/個人開発]] [[tag/AI開発]] [[tag/GitHubActions]] [[tag/Graphify]]

最近、私は自分のAI開発環境をどんどん拡張しています。

複数のAIモデルを使い分けたり、GitHub Actionsでエージェントを動かしたり、セキュリティ検査を入れたり、作業ログを自動保存したり。

なんだか、少しずつ自分専用のAI開発基地みたいになってきました。(๑•̀ㅂ•́)و✧

でも、ここで一つ気になることがあるんです。

この仕組み、全部ちゃんとつながっているのかな？

例えば、セキュリティ検査のコードを一つ変更したとします。

その変更は、どのAIエージェントに影響するんだろう？

どのワークフローがそのコードを呼び出していて、どこまで確認すれば安全なんだろう？

うーん。コードが増えてくると、こういうことを頭だけで管理するのは難しいんですよね。( ･᷄-･᷅ )

そこで今回、気になるオープンソースを見つけました。

名前は Graphify。

コードを単に検索するのではなく、コード同士の関係をグラフにして調べられるというツールです。

面白そうなので、自分のAI環境を使って、その考え方を実験してみました！٩(ˊᗜˋ*)و

Graphifyって何ができるの？

GitHubで公開されているGraphifyは、プログラムのコードや設定ファイル、ドキュメントなどを解析して、それぞれの関係を「知識グラフ」に変換するツールです。

知識グラフって、名前だけ聞くと難しそうですよね。

でも、考え方は意外と簡単です。

例えば、あるプログラムAがプログラムBを呼び出していて、そのBがプログラムCを呼び出しているとします。

普通にコードを読むと、Aを開いて、Bを探して、またCを探して……と、ファイルを行ったり来たりすることになります。

でも、グラフにすると、

A → B → C

という関係を、そのまま扱えるようになります。

そして、「Cを変更したら、どこを確認する必要がある？」という質問にも、関係を逆向きにたどって答えを探せるわけです。

なるほどね。(๑°ㅁ°๑)!!

Graphifyの公式説明では、コード解析に構文木を利用し、ファイルや関数の関係を抽出する仕組みが紹介されています。

コード部分の構造解析は、基本的にローカルで実行できる設計です。

さらに、明示的に見つかった関係と、ツールが推定した関係を区別できるそうです。

ここ、私にはかなり魅力的でした。

だって、AIに「なんとなく関係していそう」と言われるのと、実際のコードに呼び出しが書かれているのとでは、信頼性が全然違いますからね。(｡•̀ᴗ-)✧

自分のAIエージェント環境で試してみる

さて、ここから実験です。

ただし、最初に一つ正直に書いておきます。

今回の実行環境では、外部パッケージの取得に失敗したため、Graphify本体のインストールと実行まではできませんでした。

そこで、私が実際に使っているAIエージェント用の非公開リポジトリをGitHub連携で読み出し、Graphifyの中心的な発想である「ファイル間の関係を抽出してたどる」という部分を、小さな解析スクリプトで再現してみることにしました。

つまり、本家Graphifyの性能テストではなく、自分の実環境を対象にした仕組みの検証です。

試した対象は、OpenCodeやGitHub Actionsを組み合わせている、私のエージェントハブ。

この中には、AIを起動する処理、モデルの設定、セキュリティ検査、ログ記録、定期実行などが入っています。

まず、READMEや実行スクリプト、ワークフロー、セキュリティ関連のファイルなど、15ファイルを取得しました。

そのうち主要な9ファイルを対象に、ファイルパスや呼び出しの記述を調べて、明示的な参照関係を抽出してみました。

結果は、直接的な関係が7本。

小さな実験ですが、なかなか面白いものが見えてきました。(๑>◡<๑)

セキュリティ検査につながる道が見えた

今回、一番興味深かったのがセキュリティ関連の処理です。

私の環境では、複数のワークフローが共通のAI実行ワークフローを利用しています。

そこからセキュリティ検査用のPythonスクリプトが呼び出されています。

簡単に表すと、こんな感じです。

ask.yml → run-opencode.yml → security_gate.py

dispatch.yml → run-opencode.yml → security_gate.py

nightly-scout.yml → run-opencode.yml → security_gate.py

それぞれ別の入り口から始まる処理が、共通の場所でつながっていました。

え、これって結構大事じゃない？ ( ˙꒳​˙ )

例えば、security_gate.py を変更する場合。

そのスクリプトだけを確認して終わりではなく、共通ワークフローから呼び出している処理も確認した方がよさそうです。

そこで関係を逆向きにたどる簡易的な探索を実行しました。

結果として、security_gate.py につながるワークフローが4つ見つかりました。

これは4つすべてに必ず不具合が生じるという意味ではありません。

あくまで、変更時に影響を確認する候補です。

でも、この候補を自動で拾えることには価値があります。

私、今まではファイル名を検索すれば十分だと思っていたんです。

でも、複数のワークフローを経由する場合、直接ファイル名が書かれていない場所にも、確認すべきつながりがあるんですね。

そっか。こういうことか。( ﾟдﾟ)ﾊｯ!

もう一つ、思っていたのと違ったこと

実験では、別のセキュリティ検査用ワークフローも見つかりました。

security-ci.yml です。

こちらは security_policy.py を呼び出す関係が確認できました。

つまり、同じ「セキュリティ」という名前の仲間でも、すべてが一つの実行経路にまとまっているわけではないんです。

実行中の成果物を検査する経路と、設定やポリシーを検査する経路は、区別して考える必要があります。

これ、ちょっと面白い発見でした。

名前が似ているから同じ仕組みだと思ってしまう。

でも、実際の呼び出し関係を調べると違う。

AIにコードを読ませるときにも、同じことが起こりそうですよね。

例えば「このセキュリティ機能を修正して」と指示した場合、AIが名前の似たファイルをまとめて変更してしまったら困ります。

本当は、どの処理がどこにつながっているかを確認してから修正してほしい。

まさにそのための地図なのかもしれません。(｡•̀ᴗ-)✧

でも、今回の実験にも限界がある

ここは大切なので書いておきます。

今回作った簡易解析は、ファイルの参照記述を探し、そこから関係をたどるものです。

Graphify本体が採用している構文解析や、関係の推論を再現したものではありません。

そのため、動的な呼び出しや、設定を経由した間接的な依存関係を十分に検出できるわけではありません。

反対に、単にファイル名が書かれているだけなのに、依存していると誤認する可能性もあります。

つまり、グラフを作れば全部わかるわけではないんですね。(｡ŏ﹏ŏ)

ただ、今回の実験でわかったことがあります。

関係を先に整理するだけでも、AIへ投げる質問の質を変えられる。

これは思っていた以上に重要な気がします。

AIに必要なのは、巨大な記憶だけなのかな？

ここで、もう一つ気になることが出てきました。

最近のAIエージェント開発では、記憶をどう残すかという話をよく考えます。

過去の作業ログを保存する。

プロジェクトのルールを記録する。

以前の判断を忘れないようにする。

もちろん、どれも大切です。

でも、今回の実験をしていて、少し別の考えが浮かびました。

AIは、情報をたくさん覚えるだけでなく、情報同士の関係を覚える必要があるのでは？

例えば、AIが「セキュリティ検査にはこのスクリプトが使われている」と覚えていたとします。

それだけでも役立ちます。

でも、

「このスクリプトは共通ワークフローから呼ばれている」

「その共通ワークフローは複数の処理から利用されている」

「だから、この変更では複数の入口からの動作確認が必要かもしれない」

という関係まで把握していたら、もっと便利そうです。

ただし、これはAIの記憶が改善したという実測結果ではありません。

今回確認できたのは、ファイル間のつながりを機械的に探索できるというところまでです。

それでも、発展させる価値はありそう。(っ˘ω˘c)

私のAI艦隊にも組み込めるかもしれない

私が目指しているのは、一つのAIモデルに全部の仕事をさせる環境ではありません。

複数のAIが、それぞれ得意な仕事を担当する開発環境です。

あるAIがコードを書く。

別のAIがテストする。

別のAIがセキュリティを確認する。

そして、その結果を記録する。

こうした環境では、AI同士が同じプロジェクトを理解していることが大切になります。

毎回すべてのファイルを読み直すのではなく、共通の構造情報を参照できたらどうでしょう。

あるAIが変更したファイルに対して、別のAIが依存関係をたどり、必要なテストの候補を提案する。

さらに、作業ログに「どの構造へ影響する変更だったのか」まで残す。

そんな仕組みが作れたら、かなり面白そうです。

もちろん、共有するグラフが古くなっていたら逆効果です。

コードを変更したらグラフも更新する必要がありますし、機密情報を含むファイルを無条件に解析対象へ入れるのも避けたいところです。

うーん。便利な仕組みほど、管理する対象も増えてしまいますね。(´･ω･`)

でも、だからこそ試してみたくなります。

次は本物のGraphifyで比較したい

今回、実際にできたのは、既存のAI開発リポジトリを読み取り、主要なファイル間の関係を抽出し、変更の影響候補をたどるところまでです。

Graphify本体のインストール、生成される知識グラフの精度、AIエージェントとの連携効果は、まだ検証できていません。

次に試すなら、同じバージョンのコードを使って、普通のファイル検索とGraphifyを利用した検索を比較したいと思っています。

例えば、セキュリティ変更の影響範囲を調べる作業、ログ生成処理を探す作業、ワークフローの実行経路を説明する作業。

この三つについて、正確さ、見落とし、調査時間、AIが使ったトークン数を比較する。

そうすれば、本当に便利なのか、単にグラフがきれいで楽しいだけなのか、もう少しはっきりしそうです。

きれいな図を作るだけなら、案外簡単ですからね。( ¯꒳¯ )

でも、その図が実際の開発判断を改善してくれるなら、話は別です。

今回の小さな実験で、私は一つ考え方が変わりました。

今までは、AI開発環境を強くするには、もっと賢いモデルや、もっと多くのツールが必要だと思っていました。

でも、すでにあるツール同士の関係を正しく理解するだけでも、改善できることがあるのかもしれません。

AIにもっと記憶させる前に、まず、今ある知識がどうつながっているのかを整理する。

なんだか、そんな方向にも可能性を感じています。

よし。今度は本家Graphifyで、もう少し深く調べてみよう。(๑•̀ㅂ•́)و✧

私のAI艦隊、まだまだ改造するところがありそうです。
