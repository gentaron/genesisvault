# AIエージェントの過去ログを検索できる記憶にする「funes」。引き継ぎメモより8倍安いらしい

[[tag/AIエージェント]] [[tag/ClaudeCode]] [[tag/オープンソース]] [[tag/開発環境]] [[tag/HuggingFace]]

一昨日、Hugging Face が funes というコマンドを出した。

何をするものかというと、パソコンの中にもう溜まっている「AIエージェントとのやり取りの記録」を、まとめて検索できる記憶に変えてくれる。

Claude Code、Codex、pi、Hermes。この4つが勝手に吐き出しているセッションのログを読み込んで、細かく切って、意味で引ける形に並べ直す。そのうえでエージェント本人に recall という道具を持たせて、作業の途中で自分の過去を勝手に引っ張り出させる。人間が「そういえば前にさ」と言い出す前に、機械の側が思い出す。そういう作りになってる。

え、これ出ちゃったんだ、と思った。

だってこれ、いちばん地味に困ってたところなんだよね。エージェントって毎回まっさらで始まる。三日前に二時間かけて詰めた「あれはこういう理由でダメだった」が、次の窓を開けた瞬間に消えてる。だから毎回わたしが説明し直す。説明し直すのが面倒だから引き継ぎメモを書く。

メモを書かせるのにもトークンを払う。なんか、記憶を持たない相手に毎朝自己紹介してる気分になってた。

で、funes がおもしろいのは、この「どうやって前回を次回に渡すか」を、ちゃんと測って比べているところ。ベンチマークが丸ごとデータセットとして公開されてて、受領証まで全部置いてある。

やり方は5つ。何も持たずに新しい窓を開ける。引き継ぎメモを書いて渡す。funes で過去を検索させる。窓を切らずに全部の文脈を引きずったまま続ける。窓を切らずに要約（compact）だけ残して続ける。同じ課題、同じ採点、同じ出発点で、渡し方だけを変えて回す。

数字がけっこうえぐい。ひとつめの課題だと、引き継ぎメモが851k、全文脈を持ったままが822k、要約が778k。それに対して検索が101k。重みづけしたトークンの数え方をしていて、成功1回あたりの費用として並べてある。だいたい8倍の差。もうひとつの課題では検索が169k、引き継ぎメモが637kで、こっちは4倍弱。何も持たない組は、両方とも最後まで正解に届かなかった。届かない課題を選んでいる、というのが前提条件になってる。

わたしが一番ぞっとしたのは要約の話のほう。556,870トークンぶんの会話を、要約が4,155トークンに畳んだ。134分の1。

すごいなと思うでしょ。でもそのとき落ちたのが「試した4つのうち2つは、やったら逆に悪くなった」という部分だった。要約には「どれも効果なし」としか残らなかったから、続きを引き受けたエージェントは「特に何もなかったのね」と読んだ。3回やって3回とも同じ読み方をした。採点で聞かれるのが、まさにその落ちた2つ。

「効果がなかった」と「やったら悪化した」は、要約すると同じ顔になる。これ、わたしも人にやってる気がする。うまくいかなかった話をまとめるとき、失敗の中身まではだいたい書かない。

なので、この道具が売っているのは検索の速さじゃなくて、たぶん「畳まないでおく」という選択肢のほうなんだと思う。

中身は思ったより小さい。Rust製の単体のコマンドで、記憶は Lance という形式のテーブルとしてローカルに置かれる。埋め込み（文章を数字の並びに変えて意味で引けるようにする処理）に使っているのは bge-small-en-v1.5。パラメータは3300万くらい、ファイルは127MBちょっと。7Bとか出てこない。だからGPUなしのノートでもこの部分は普通に回る。検索は意味の近さと、単語そのままの一致を混ぜて、最後に並べ直す。固有名詞やエラー文みたいな「そのままの文字列」も落ちにくいようになってる。

容量の見当もついた。公開されている保存庫のファイルサイズを、入っている塊の数で割ってみたら、1塊あたりだいたい2KB。Hugging Face 自身が公開している funes の記憶が27,118塊で54.5MB。別に置いてある200セッションぶんの保存庫が155,361塊で301MB、1セッションあたり1.5MBの計算になる。ベクトルの実体（384次元×4バイト）だけで228MBだから、中身の75%は数字の並びってこと。数百セッション溜めても1GB行かない。これはうれしい。

でも、正直に書くと、今日わたしのノートには素直には入らない。

配ってるバイナリが Linux の x86_64 と aarch64、それと Apple Silicon の Mac の3つだけ。Windows用がない。

入れるなら WSL を用意するか、Rust のツールチェーンと protoc（Protocol Buffers のコンパイラ）を揃えて自分でビルドするかになる。実効メモリ6GB弱の機体で Rust のリリースビルドを回すのは、できなくはないだろうけど、たぶんファンがうるさい夜になる。しかも Linux 版は glibc 2.35以上という条件つき。ここは素直に、今日の自分の環境では待ちだと思った。

あと気になっているのが、埋め込みモデルが英語向けだということ。bge-small-en。わたしのやり取りは日本語混じりなので、意味で引くほうはたぶん弱い。単語一致のほうで拾えるかもしれないけど、そこはまだ確かめてない。埋め込みモデルは記憶に焼き付けられる仕様で、あとから変えたければ生ログから作り直しになる、とも書いてある。日本語で使うなら、最初にどのモデルを選ぶかが地味に効いてきそう。

お金の話は気持ちいい。本体は Apache 2.0 で無料。索引を作るのも検索するのも全部ローカルで完結するから、ここにAPI代はかからない。かかるのは ask、つまり「思い出した内容をもとに答えて」とエージェントを借りるときだけ。

無料枠を数えながら回している身としては、この線の引き方はありがたい。記憶を Hub に上げる機能もあって、こっちは既定で非公開のデータセットになる。上げる前に秘密っぽい文字列を弾く仕組みも別に入っている。とはいえ、自分の作業ログを全部クラウドに置くかというと、わたしはたぶん最初はローカルだけで様子を見る。

これが来たなら、次は「/compact しかない」状態のほうが古く見えてくるんじゃないかな。会話が長くなったら畳む、というのが当たり前だったけど、畳まずに外に出して必要な時だけ引く、が並ぶ。

そうなると要約の腕前じゃなくて、どこに置いてどう引くかの設計のほうに話が移る。もうひとつ、記憶がデータセットとして公開できる形になった時点で、たぶん「チームの記憶」を配る人が出てくる。あるプロジェクトの過去2年ぶんの判断が入った記憶を、新しく入った人のエージェントに丸ごと渡す。悪くないけど、間違った判断も一緒に配られる。

そのうえで、あんまり持ち上げすぎないでおきたい。これは検索であって、理解じゃない。過去の自分が間違ったことを言っていれば、それをそのまま自信たっぷりに引っ張ってくる。しかも引いてきた文章には出典がつくから、余計に本当っぽく見える。記憶があるって、正しさとは別の話なんだよね。

それでも触ってみたい。名前が funes なのがずるい。全部を覚えていて、そのせいで何も考えられなくなった男の話から取ってる。作った側も、たぶん分かってて付けてる。
