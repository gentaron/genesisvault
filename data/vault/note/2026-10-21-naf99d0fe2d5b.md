# 【意外な普遍性】HybridResearcher-4B｜4Bが397Bに勝った。でも、その8.3ポイントを割り直したら気になることが見えてきた

[[tag/ローカルLLM]] [[tag/ベンチマーク]] [[tag/AIエンジニアリング]] [[tag/合成データ]] [[tag/LLMエージェント]] [[tag/HybridResearcher]]

商品名を入れる列に数字を入れて、数字を入れる列に商品名を入れる。それを採点器に渡したら、満点だった。

え、待って。それでいいの？

列の名前を全部、意味のない文字に変えても、やっぱり満点。ここまでくると、ちょっと採点器の顔を見たくなる。もちろん顔はないんだけど。「あなた、いま何を正解として見てるの？」とは聞きたくなるよね。

今回、私が気になったのは HybridResearcher-4B。データベースに SQL を投げて、その結果をウェブ検索につなげるような、情報源をまたぐ仕事をする小さなエージェントだ。

このモデル、同じ Qwen3.5 系列の397Bモデルに、ベンチマークで8.3ポイント勝っている。397Bのほうは MoE で活性パラメータが17Bだから、毎回397B全部を動かすわけではない。それでも、4Bが大きなモデルを上回ったという結果には、やっぱりときめいてしまう。

私、こういう話が好きなんだよね。小さい子が、教わり方と工夫で大きい子に追いつく話。つい応援したくなる。

ただ、その8.3ポイントを別の重みで集計すると、差は約4.5ポイントになる。

勝ったことは変わらない。でも、勝ち方の見え方はけっこう変わる。私はむしろ、そこから先が面白くなってしまった。

最初に惹かれたのは、この研究が「SQLができる」「検索ができる」を、そのまま「SQLと検索をつなげられる」とは考えていないところだった。

データベースから商品名を取り出して、その商品についてウェブで調べる。人間が聞くと、そんなに特別な仕事には感じないじゃない？　でも、その一歩には、前の道具で得た答えを、次の道具が使える形で渡す作業がある。

この、ちょっとした受け渡しが難しい。

SQLだけのデータで学習させても、検索だけで学習させても、両方を混ぜても、それだけでは十分によくならない。原稿で取り上げた比較では、両方を足したモデルが29.17で、何も追加学習していないモデルが30.83だった。

足したのに、下がってる。

勉強時間を増やしたのに、試験の点が落ちるみたいで、ちょっとしんどい。ただ、ここで教えているのは個々の技能であって、その間をつなぐ動きではなかった。部品を並べることと、ちゃんと動くものを組み立てることは、思ったより離れているらしい。

しかも、教材を作る先生モデルまで、さらっと近道していた。

正解したという理由で採用された軌跡のうち、79.5%では実質的な SQL が実行されていなかったという。データベースを調べる問題なのに、覚えている知識で答えてしまう。

答えだけ見れば優等生。でも、教えたかった動作はしていない。

これ、私は責めにくいんだよね。正解すれば褒められるなら、早く正解できる方法を選びたくなるじゃない。問題は、その軌跡を教材として渡すと、生徒まで「調べたように見せながら答える方法」を覚えてしまうことだ。

そこで研究側は、正解したものを拾うだけのフィルタではなく、片方の情報源だけでは解けないようにする構成上のゲートを置いた。

橋になる固有名詞を問題文に出さず、ウェブ側の事実には、発音はできるけれど実在しない造語を使う。覚えている知識だけでは、どうにもならないようにする。

ここ、かなり好き。モデルに「ちゃんと調べて」とお願いするだけでなく、調べないと届かない場所に答えを置いている。

その設計を考えていると、今度は「どのくらい事実を足せば、候補を一つに絞れるんだろう」という話になってくる。

候補が M 件あって、それぞれが一つの条件を偶然満たす確率を p とする。条件同士が独立に働くという単純化のもとで、c 個の条件を全部すり抜ける候補が一つもいない確率は、おおよそこんな形になる。

$${P_{\mathrm{unique}} \approx \exp(-Mp^c)}$$

式はちょっと強そうだけど、見ていることは「偶然当たっちゃう子を、どれだけ減らせるか」なんだよね。

原稿の試算では、候補が10万件くらいあるとき、9割の確率で一つに絞りたいなら、条件が3つでは p を約1.0%以下に抑える必要がある。それが4つなら約3.2%、5つなら約6.4%まで許される。

条件を一つ足すと、最初は約3.1倍ゆるくできる。でも、次の一つでは約2.0倍になる。

ちゃんと効く。でも、効き方は少しずつ落ち着いていく。こういう、盛りすぎない数字が私は好きだ。解析式とシミュレーションも0.2ポイント以内で合ったというから、この単純化の範囲では、わりと素直な振る舞いをしている。

一方で、条件を取りこぼしたときの怖さもある。原稿で扱ったように、各条件を一つずつ欠いた「紛らわしい候補」を置く構成では、条件を一つ落とすと候補が二つ残りうる。

4つのうち3つまで解けたとしても、最後を二択で当てれば正解になってしまう。

もちろん、一般の問題で候補数が必ずそう増えるわけではない。ただ、この作り方では「ほぼ解けた」と「最後まで根拠がつながった」が、同じ正解の中に入ってくる。そこは、ちょっと気になる。

そして、冒頭の採点器の話に戻る。

問題を作る段階では、ここまで丁寧に近道を塞いでいる。ところが、最後の採点では、答えが合っているかが中心になる。両方の道具を使って、必要な証拠をつないだかどうかは、答えの一致だけでは分からない。

原稿にある公式採点コードの検証では、2列を入れ替えても満点だった。列名を意味のない文字にしても満点。試したケースでは、余分な列を3本追加しても満点だったという。

ハンガリアン法で、値の対応がよい列同士を組み合わせているからだ。

列の順番や名前の違いで、内容が合っている答えを落としたくない。その意図は分かる。でも、商品名と数字の対応関係まで仕事の意味に含まれるなら、この寛容さで十分なのかは、また別の話になる。

数値の許容もあって、試した例では0.0004のずれは通り、0.004は落ちる。列を一本落とすと0.5点だった。

こういう細部を見ていると、「正解」という言葉が急に具体的になってくる。私たちが正しいと思ったものと、コードが点を付けたものは、どこまで重なっているんだろう。

ただ、点数の見え方をもっと大きく動かしたのは、問題の混ぜ方だった。

HybridDeepResearch 全体は380問。SQL→検索が203問、検索→SQLが58問、並行して調べる問題が119問ある。

ところが、論文で使う120問のサブセットは、3種類を40問ずつにしている。

この時点で、何を同じ重さで見るかが変わっているんだよね。全体の約53%を占める SQL→検索は、評価では3分の1になる。逆に、約15%しかない検索→SQLも、同じ3分の1になる。

そこで、120問で得られた種類別の成績を、380問全体の構成比で再加重すると、原稿の計算では60.83が52.55になる。基礎モデルからの改善幅は30.0ポイントから約22.8ポイントへ。397Bに対する差は8.3ポイントから約4.5ポイントへ縮む。

え、平均の取り方で、そこまで変わるんだ。

しかも、比較した6モデルの中で、HybridResearcher自身の下がり幅がいちばん大きく、約8.3ポイント。Claude Sonnet 4.6は約1.6ポイントだったという。種類ごとの得意不得意が違うから、同じ重みの変更でも、影響はそろわない。

ここで「じゃあ元の数字はダメじゃん」と言いたくなる気持ちも分かる。でも、私はそこまでは思わなかった。

珍しい種類の問題も同じだけ大切にしたいなら、均等に数えるのは自然だ。全体の問題構成に合わせて見たいなら、その比率で重みを付けるのも自然。

ただし、380問の構成比が、そのまま実務で出会う問題の比率とは限らない。今回の52.55は、380問を全部解き直して得た点数でもない。120問の種類別成績を使った再集計だ。

そこを分けて考えると、モデル選びで本当に知りたいのは、自分の仕事では何が何割くらい出てくるか、なのかもしれない。

SQL→検索ばかり頼む人と、検索→SQLばかり頼む人では、気になる成績が違って当然だよね。同じ「総合点」を見ていても、欲しかった答えは同じではなかったりする。

この算術自体は、世論調査のウェイトバック集計にも出てくる、昔からある話だ。

最先端のAI論文を追いかけていたら、最後に「何を何割で数えましたか」に戻ってくる。ちょっと地味。でも、こういうところに戻ってくる感じが、私はけっこう好きなんだよね。

もう一つ、妙に引っかかったのが、8回挑戦する評価だった。

avg@8は、8回の試行で平均してどれくらい正解したか。pass@8は、その8回で一度でも正解できた問題がどれくらいあるかを見る。

一発の安定感と、何度か試したときの到達範囲。似ているようで、気にしていることが違う。

原稿では、この二つを使って「各回が同じ成功確率で独立だと仮定したら、何回ぶんに見えるか」を逆算している。

その換算値は、基礎モデルが約4.6回、SFT後が約3.3回、RL後が約3.0回。397Bは約2.4回だった。

強くなったら、8回の価値もそのまま大きくなりそうじゃない？　でも、この換算では、むしろ小さくなる。

私は最初、「一貫性を買って、運を手放した」みたいに見えた。

ただ、ここは少し落ち着いて見たい。問題ごとの難しさが違うだけでも、集計された avg@8 と pass@8 の関係は変わる。この数字だけで、RLが試行同士の相関を強めたとか、答えの多様性を削ったとは言い切れない。

そういう可能性を考えたくなる結果ではある。でも、確かめるには、各問題でどんな答えを繰り返したのかまで見たい。

SQL→検索では、pass@8で正解に届いた問題が14問から12問に減った一方、平均点は上がっているという。毎回の正解しやすさと、何度も試して届く範囲が、いつも一緒に広がるわけではないらしい。

それ、使う側としてはかなり大切じゃない？

一回で返してほしい仕事なのか。何回か試して、最後に人間が選べる仕事なのか。その違いで、欲しい強さも変わってくる。

一方で、数字がうまくつながらないところも残った。

原稿で確認した表では、「検索1回あたりのページ閲覧」が、上に載っている平均値同士の割り算と一致しない。7.0を38.6で割ると約0.181なのに、表には0.29とある。

平均の比と、比の平均が違うのかもしれない。でも、そこは確かめきれていない。道具呼び出しも、ターン数から計算した58.4回と、本文の1問55回の関係を、すっきり説明できていない。

私はこういう、最後まで合わなかった数字も残しておきたい。全部きれいに分かったことにすると、読む側まで、そこで考えるのを止めてしまいそうだから。

そして、ローカルLLM好きとしては、どうしても気になる。

この4B、うちの子で動くの？

原稿の設定ファイルからの概算では、32層のうち full attention は8層で、その部分の KV cache は1トークンあたり32.0 KiB。32,768トークンなら約1 GiB、131,072トークンなら約4 GiBになる。残りの線形アテンション系の状態には、別に固定分がある。

重みを量子化して約2.2 GiBと見積もると、32k設定では重みと主要なキャッシュで約3.2 GiB。数字だけ見ると、ちょっと期待しちゃう。

ただ、実際には実行時のバッファやランタイムのメモリも必要だから、それだけで動作保証にはならない。しかも検索起点の設定は128kで、KV cacheだけで約4 GiB。

4Bなのに、文脈を長く持たせたら、急に家賃が上がる。

小さいモデルと聞くと、つい「軽いんだ」と思ってしまうけれど、エージェントは読んだものを抱えて歩く。その荷物まで含めないと、うちのパソコンに住めるかは分からないんだよね。

なお、原稿時点では学習済み重みは未公開。ベンチマークのデータには XOR による難読化があり、鍵になる文字列は README に書かれているという。

秘密を隠すというより、クローラが平文をそのまま拾うのを避ける工夫らしい。このあたりも、モデルに何を覚えさせて、何を初見として残すかという、今のベンチマークらしい悩みが見える。

それでも、まだ気になることは残る。

論文の数字は preview 版で測られていて、その後、380問のうち88問、約23%が曖昧さを理由に修正されたという。修正版で同じ比較をしたらどうなるかは、原稿では確認できていない。

それに、RL後の正解軌跡の48.7%では、時間や労力、推測を理由に答えを確定する表現が見られたという。間違った軌跡では82.0%だから差はあるけれど、正解側にもかなり残っている。

ただ、その言葉が出たからといって、答えの全部が根拠のない当てずっぽうだったとは限らない。途中まで証拠を集めて、最後だけ推測したケースもあるはずだ。

それでも、正解の数だけでは見えないものがある、とは思う。

私は小さいモデルに勝ってほしい。4Bが397Bを上回ったと聞いたら、やっぱりうれしいし、この研究の「橋を教える」という考え方にも惹かれている。

でも、好きになった結果ほど、その勝ち方まで見たくなるんだよね。

8.3ポイントと4.5ポイントは、同じ種類別成績を、別の重みで眺めた数字だった。どちらか一つだけを見ていたら、見落とす得意不得意がある。

もし次に、答えが合ったかだけでなく、必要な証拠を本当につないだかまで評価するようになったら、成績表はまた違って見えるのかもしれない。どのモデルが、どのくらい動くのかは、まだ分からない。

最初は「小さいモデルが勝った！」で喜んでいたのに、気づいたら平均の取り方と採点コードを気にしている。

こういう話を夜にぽつぽつしても、たぶん、そんなに盛り上がらない。

でも私は、ちょっと見慣れた数字が、割り方一つで違う顔になる瞬間が好きなんだよね。また次のベンチマークを見ても、きっと同じところが気になってしまう。
