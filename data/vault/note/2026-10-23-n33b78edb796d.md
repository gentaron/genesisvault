# 【AIと脆弱性の転換点】PHP・Node.js・Next.js・LiteLLMで何が起きた？｜「見つける速度」に「直す速度」が追いつかなくなる時代

[[tag/AIエージェント]] [[tag/PHP]] [[tag/脆弱性]] [[tag/AIセキュリティ]] [[tag/Nodejs]]

2026年10月21日。PHPとNode.jsで重大な脆弱性が公表された。

最初は、またセキュリティの大きなニュースが来たんだな、くらいに思っていた。でも、関連する発表を追いかけているうちに、なんとなく気味の悪いものを感じ始めたんだよね。

これ、単にPHPやNode.jsに問題が見つかったという話じゃないのかもしれない。

Next.js、Laravel、GitLabでも重大な脆弱性が報告されている。AI開発で使われるLiteLLMでは、公式の配布物そのものが攻撃者に改ざんされた。

そして、脆弱性を発見した側には、GeminiやCodex SecurityのようなAIがいる。

なんというか、ソフトウェアを作る側も、それを壊そうとする側も、急に時間の流れが変わり始めている気がする。

私が今回気になったのは、そこなんだよね。

PHPの脆弱性は、公開される前から狙われていた

まず、PHPの話から。

10月21日に公表された「PHP2Shell」は、CVE-2026-109618とCVE-2026-109619という2件の脆弱性を指している。

どちらもPHPのメモリ処理に関係していて、条件がそろうと、ログインしていない外部の攻撃者がサーバー上でコードを実行できる可能性がある。深刻度はCVSS v4.0で9.2。

個々のWebサイトのプログラムが雑だったから、という話ではない。PHPという実行基盤そのものに問題があった。

PHPで動くWordPressなども、PHPのバージョンや実行環境によっては影響を受ける。アプリケーションのコードを書き換えていなくても、その下で動くPHPが古ければ危険になり得るわけだ。

修正版はPHP 8.5.12、8.4.27、8.3.36、8.2.35。PHP 8.1以前は公式サポートが終了しており、PHP本体から今回の修正は提供されない。

でも、私がもっと引っかかったのは、その日付だった。

AWSの調査によると、10月17日の時点ですでに悪用の試みが観測されていた。正式な発表より4日前だよ。

そして21日の公開後には、攻撃用の実証コードが短時間で出回り、AWSの観測網に対する攻撃も増えた。

もちろん、観測された攻撃がすべて実際のサーバー侵害に成功したわけではない。そこは区別しないといけない。

それでも、これまでは脆弱性が公表されてから修正を考えればよかった、という感覚があったとしたら、もう危ないのかもしれない。

脆弱性の公開日が、攻撃の開始日とは限らない。

これって、結構大きな変化じゃない？

参考：AWSによるPHP2Shellの攻撃観測

Node.jsでは、AIが重大な問題の発見に関わっていた

同じ10月21日、Node.jsもセキュリティ更新を公開した。

特に重大なのがCVE-2026-111497。Brotliというデータ圧縮方式の展開処理で、メモリの範囲外に書き込んでしまう問題だ。条件によってはリモートコード実行につながる。

ほかにも、TLS証明書の検証が回避される問題、DNSの名前を不適切に処理する問題などが修正された。

修正版はNode.js 22.23.4、24.22.1、26.12.1。

ここで面白いのが、Brotliの問題の発見者として、Node.jsの公式発表にOpenAI Codex Securityが記載されていること。

AIがコードを読んで、攻撃につながる欠陥を調べ、それを人間が検証して修正につなげている。

AIによるコード生成は、もう珍しくない。でも、コードを書いていたAIが、今度は何年も使われてきたコードの奥に潜んでいる欠陥を探している。

私はこの役割の変化が、かなり面白いと思っている。

ソフトウェアを作る速度だけが速くなると思っていたら、ソフトウェアの欠陥を発掘する速度まで変わり始めたんだよね。

参考：Node.js公式セキュリティリリース

しかも、問題はPHPとNode.jsだけではなかった

少し範囲を広げてみると、10月中旬にはほかの重要なソフトウェアでも修正が相次いでいる。

10月14日のNext.jsでは、画像最適化に使うライブラリの問題から、特定のLinux環境でリモートコード実行につながる脆弱性が公開された。

もう一件、App Routerの特定のキャッシュ機能でも、条件がそろうとコードを実行される問題が見つかっている。

修正版はNext.js 15.5.28と16.4.1。ただし、後者のキャッシュ機能の問題は16系が対象なので、影響する条件を正しく確認する必要がある。

10月19日にはLaravel。特定のトークン認証設定とデータベース条件の組み合わせで、有効なAPIトークンを知らなくても、別のユーザーとして認証される可能性があった。修正版はLaravel 12.68.0と13.29.0だ。

10月21日にはGitLabでも、CVSS 10.0の脆弱性が修正された。正規表現を処理する部分の整数オーバーフローが原因で、条件によっては認証なしでサーバー上のコードを実行できる可能性があった。GitLab 19.5.1など、複数の系列で修正版が出ている。

そして、Web開発ツール以外にも目を向けると、Cisco Secure Email Gatewayでは10月14日に深刻度9.8の問題が公表され、実際の悪用も確認されている。

さらに10月17日には、認証局eMudhraの中間証明書8件に関係する秘密鍵の侵害が報告された。これは偽のHTTPS証明書を発行できる危険につながる問題で、MozillaはFirefox側で対象証明書を緊急ブロックした。

なんだか、Webのいろんな場所が同時に揺れているように見えてくる。

ただ、ここは慎重に考えたい。

これらは原因も発見者も影響範囲も違う、別々の事件だ。一つの巨大な攻撃がすべてを引き起こしたという証拠はないし、すべてAIによって発見されたわけでもない。

それでも、私が気になるのは、いろんな基盤が持っていた問題が次々に見えるようになっていることなんだよね。

Claudeは6,157件の脆弱性を報告していた

この違和感をさらに強くしたのが、Anthropicが10月2日に公開した数字だった。

Claude Mythos Previewなどのモデルを使った調査によって、591のオープンソースプロジェクトに対し、6,157件の脆弱性が報告されたという。

6,157件。

正直、私は最初、この数字を見て少し固まった。

もちろん、この数字をそのまま「6,157件の重大なゼロデイが確認された」と読むのは間違いだ。深刻度はさまざまで、報告には人間による検証を経たものと、それ以外の経路で提出されたものが含まれる。

同社が把握している修正済みの件数は、10月2日時点で516件だった。

ここで問題になってくるのが、発見と修正の速度差だと思う。

AIは大量のコードを調べられる。でも、見つかった問題が本当に危険なのかを確認し、影響を調べ、修正し、既存の機能を壊さないかテストして、利用者に更新してもらうところには、まだ多くの人間の作業が残っている。

発見が速くなるのはいいことだ。

でも、発見した問題を処理する仕組みまで同じ速度で進化しなかったら、どうなるんだろう。

欠陥の一覧だけがどんどん長くなっていくのかな。

いや、それは普通に困るよね。

参考：Anthropicの脆弱性報告ダッシュボード

LiteLLMの事件は、もう一段違う問題を見せていた

そして、今回の一連の出来事の中で、私が特に怖いと感じたのがLiteLLMだった。

LiteLLMは、複数のLLMのAPIをまとめて扱うために使われるソフトウェアだ。AIモデルごとに異なる接続方法を整理して、ひとつの窓口から呼び出せるようにする。

便利なんだよね、こういう仕組みは。

でも、複数のAIサービスをつなぐということは、その場所にいろんなAPIキーや認証情報が集まりやすいということでもある。

10月21日、そのLiteLLMの公式リリース工程が侵害された。

攻撃者は開発者3人分のGitHub認証情報を悪用し、正規のリリース処理を操作して、マルウェアを含むLiteLLM 1.107.0をPyPIやDockerの配布先に公開させた。

しかも、公式GitHubにある同バージョンのソースコード自体には、問題のマルウェアが含まれていなかった。

ここ、かなり嫌な話じゃない？

ソースコードが正常でも、そこから利用者に届く配布物が正常とは限らない。

しかもLiteLLM側の調査では、Claude Codeの応答にGitHub CLIのOAuthトークンが含まれ、それがログに残る状況が観測されていたという。

攻撃者はインターネットに公開された社内LiteLLM環境に侵入し、そのログから認証情報を得た可能性があると説明されている。ただし、最初の侵入経路は10月21日時点の報告では確定していない。

AIが直接この事件を引き起こした、と断定するのは違う。

でも、AIの応答、ログ、認証情報、ソフトウェアの配布工程が、一つの攻撃経路としてつながり得ることは見えてきた。

攻撃されたのは、利用者が書いたアプリケーションだけじゃない。

そのアプリケーションを作り、動かすための道具そのものだった。

参考：LiteLLM公式インシデント報告

これが本当の転換点なのかもしれない

ここまで見ていて、私は少し考え方が変わった。

以前のセキュリティ対策って、どこか「問題を見つけたら直す」という発想が中心だった気がする。

もちろん、今でもそれは必要だ。

でも、AIが脆弱性の発見を速くして、攻撃者も公開された修正内容を素早く分析できるようになると、修正版が出てから数日以内に対応すればいい、とは限らなくなる。

AWSも今回のPHP2Shellを受けて、インターネットに公開された重大な脆弱性では、対処時間を日単位ではなく時間単位で考える必要があると指摘している。

これは結構な話だと思う。

人間の作業時間は、急に100倍にはならないから。

だから、これから重要になるのは、発見するAIをさらに賢くすることだけではなくて、発見から修正までの流れを短くする仕組みなのかもしれない。

ここで初めて、セキュリティ対策の自動化が、単なる便利機能ではなくなってくる。

じゃあ、具体的にどう守ればいいんだろう

ここは現実的に考えたい。

「気をつけましょう」で終わるのは、さすがに頼りないからね。

まず、自分が何を動かしているのか把握する

最初に必要なのは、ソフトウェアの棚卸しだと思う。

PHPなら php -v、Node.jsなら node -v で実行環境のバージョンを確認する。Next.jsなら npm ls next sharp、Laravelなら composer show laravel/framework で導入バージョンを確認できる。

ただし、手元のPCで確認しただけでは足りない。

本番サーバー、Dockerイメージ、クラウドのデプロイ環境、CIで使う実行環境は、手元と違うバージョンになっていることがある。

今回のPHP2Shellで必要なのは、PHP 8.5.12、8.4.27、8.3.36、8.2.35以降の修正版へ更新すること。Node.jsは22.23.4、24.22.1、26.12.1以降の対応版を使うことだ。

Next.js、Laravel、GitLabも、先ほどの公式修正版を確認して更新する。

そして、公開サーバーでPHP2Shellの影響が疑われる場合は、単に更新するだけでなく、10月17日までさかのぼってログを調べる必要がある。

更新を人間の記憶だけに任せない

次に、GitHubのDependabotを有効にしたい。

Dependabot Alertsは既知の脆弱性を通知し、Security Updatesは修正版へ更新するPull Requestを作成できる。

Node.jsの依存パッケージなら npm audit、PHPのComposer依存パッケージなら composer audit、Pythonなら pip-audit なども使える。

ただし、これらは万能ではない。

例えば npm audit はNode.js本体の更新を代わりにやってくれるわけではないし、まだ誰も登録していない新しい脆弱性をすべて検出できるわけでもない。

だから、依存パッケージの自動検査と、実行環境そのものの更新を分けて管理する必要がある。

AIを使うなら、Codex Securityのようなコード調査ツールで追加の検査を行う方法もある。ただし、AIの報告を無条件に信用せず、再現性や実際の攻撃経路を検証することが大切だと思う。

「最新版を使えば安心」とも限らない

LiteLLMの事件から学べることは、少し違う。

新しいバージョンを自動的に取り込む仕組みは、修正を早く届けてくれる一方で、悪意ある新バージョンも早く取り込んでしまう可能性がある。

だから本番環境では、ライブラリのバージョンを固定する。Dockerイメージも、できれば変更され得る latest だけに頼らず、検証済みのダイジェストで指定する。

さらに、実際に配布された成果物が、どのソースコードから、どのビルド工程で作られたかを確認する仕組みも重要になる。

GitHubのArtifact Attestationsは、そのために使える技術の一つだ。

ただ、署名があれば絶対安全というわけでもない。今回の事件では、正規のリリース工程自体が悪用されていたから。

信頼する対象を、ソースコードからビルド工程、そして配布物まで広げなければいけないんだと思う。

なお、LiteLLM 1.107.0を問題の時間帯に実行した環境では、単にバージョンを戻すだけでは足りない。

LiteLLM公式は、影響環境を侵害済みとして扱い、クリーンな環境から再構築し、接続先LLMのAPIキー、データベースのパスワード、クラウドの認証情報などを再発行するよう求めている。

調査前に影響を受けたPython環境で安易に pip install を実行することも避けるべきだ。マルウェアが再実行される可能性があるため、まず公式の復旧手順を確認したい。

最後は、AIに渡す権限そのものを小さくする

私は、ここがこれから一番重要になるような気がしている。

AIエージェントにコードを実行させたり、GitHubを操作させたり、外部サービスに接続させたりするのは、確かに便利だ。

でも、便利さのために本番環境の管理者権限、クラウドの認証情報、APIキーを全部渡していたら、一つの侵害がいろんな場所に広がってしまう。

だから、AIごとに必要最小限の権限を与える。本番用と開発用の認証情報は分離する。ログには秘密情報を残さない。認証には短期間だけ有効な資格情報を優先し、重要な操作には人間の承認を挟む。

外部のWebページやMCPツールから届いた文章も、AIへの正規の命令としてそのまま扱わない。

実際、OWASPが10月8日に整理したAI関連のセキュリティ事例でも、外部からの指示によるエージェントの誘導、過剰な権限、接続先からの情報漏えいが問題として挙げられている。

AIを信用しないというより、AIが間違えたり、だまされたりしても、被害が広がらない設計にする。

なんだか、人間の組織管理にも少し似ている気がする。

防御にもAIが必要になる。でも、それだけでは足りない

ここまで考えて、一つ面白いことに気づいた。

今まで私たちは、AIによってソフトウェアを開発する人が減るかもしれない、という話をよくしてきた。

でも、セキュリティの世界では、逆の現象も起きるかもしれない。

AIが大量の欠陥を見つけることで、修正する仕事が増える。

修正の速度を上げるためにAIを使う。

そして、そのAIが使うツールや認証情報を守るために、さらに別の仕組みが必要になる。

ここには、少し不思議な循環がある。

ソフトウェアの問題を解決するために作ったAIが、これまで見えなかった問題を次々に見つけてしまう。

問題が増えたように見えるけれど、本当は以前からそこにあったのかもしれない。

ただ、見えてしまった以上、もう見なかったことにはできない。

私は、2026年10月の出来事を、セキュリティの完成ではなく、セキュリティの前提が変わった瞬間として捉えている。

AIがどれだけ多くの脆弱性を発見できるようになるのかは、まだ分からない。人間による検証や修正が本当に追いつかなくなるのかも、現時点では断言できない。

でも、少なくとも「見つけたら、そのうち直す」という時間感覚は、少しずつ通用しなくなっているように感じる。

これからは、発見した瞬間から修正と検証が動き出すような仕組みが必要になるのかな。

そして、もしAIがそこまで担当するようになったら、今度はそのAIを誰が監査するんだろう。

考えるほど、少し怖くなる。

でも、こういう技術の転換点を眺めている時間、私は結構好きなんだよね。

たぶん、まだ始まったばかりなんだと思う。
