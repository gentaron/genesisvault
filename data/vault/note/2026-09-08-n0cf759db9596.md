# ブラウザでAIを動かす部品が、Hugging Faceで配られはじめた

[[tag/ローカルLLM]] [[tag/フロントエンド]] [[tag/HuggingFace]] [[tag/WebGPU]] [[tag/ブラウザで動くAI]]

Hugging Faceが9月1日に @huggingface/kernels というものを出した。npm で入れる JavaScript のライブラリで、やることはひとつ。

ブラウザの中でAIを動かすときに使う「GPUの計算部品」を、Hugging Face Hub から落としてきて、そのまま走らせる。ライセンスは Apache-2.0、いまのところ部品は207個ある。

計算部品、というのはカーネルのこと。ニューラルネットが内側で何万回も呼ぶ小さい計算——行列のかけ算とか、正規化とか、注意のところで使うやつとか——をGPU向けに書いた短いプログラムのこと。

ブラウザからGPUを触るときは WebGPU という仕組みを使って、そのプログラムは WGSL という専用の言語で書く。

その WGSL が、Hub のリポジトリに置いてある。モデルの重みが置いてあるのと、同じ棚に。

正直いうと、最初は「へえ」しか出てこなかった。

207個って言われても多いのか少ないのか分かんないし。

でも配ってるものの中身を見たら、面白いのは個数じゃなかった。

いままでブラウザでAIを動かすときって、ランタイム（推論を回してくれる土台のソフト）が自分の中にカーネルを全部抱え込んでた。

ONNX Runtime Web とかがそう。だから新しい演算を速くしたかったら、ランタイム本体の更新を待つしかない。カーネルは土台の内臓で、外から触るものじゃなかった。

それが今回、カーネル1個につきリポジトリ1個になった。名前も webgpu-kernels/ai.onnx.Relu みたいな感じで、ONNX の演算名がそのまま付いてる。

中には manifest.json（入力と出力の型の約束ごと）、metadata.json（どこから来たかの記録とダイジェスト）、test.json（正しさを確かめるテスト）、bench.json（速さの測り方）、それに WGSL のテンプレートが入ってる。呼ぶときは名前とバージョンを渡すだけ。

version: 1 と書くと v1 というブランチを追いかけるので、修正が入ったら勝手に付いてくる。40文字のコミットIDを渡せば、バイト単位で固定できる。

これ、モデルを読み込むときの revision 指定とまったく同じ考え方だ。モデルに付いてた「名前・版・来歴」が、GPUのシェーダー1本にも付いた。それが今回の中身だと思う。

もうひとつ、へえと思ったところがある。カーネル1個は WGSL 1本じゃなくて、variants という束になってる。

それぞれに requires という条件が付いてて、float16 のシェーダーが使えるか、subgroups（GPUの中で計算単位がまとまって値をやりとりする機能）があるか、ワークグループの共有メモリをどれだけ取れるか、みたいなことが書いてある。

読み込むときにローダーがあなたのGPUに問い合わせて、条件を満たす variant を選ぶ。

つまり「速いカーネル」は端末ごとに違う、という前提で最初から作られてる。ここがちょっといいなと思った。ひとつの正解を配るんじゃなくて、条件の違う実装を何本か持っていって、その場で選ぶ。

速さの話も一応。ONNX Runtime の WebGPU 版と比べて、幾何平均で2.5倍くらい速かった、と本人たちは書いてる。

ただしこれ Apple の M4 で測った数字。だから自分の端末で何倍になるかは、まったく別の話。しかもここに「本当の遅さ」は入ってない。

測ってるのはGPUが計算してる時間だけで、シェーダーをコンパイルする時間とデータの行き来は外してある、と自分で断ってる。ブラウザで推論するときに実際つらいのって、だいたいそっちなんだけど。

その端末ごとのばらつきを集めるために Fleet というのも一緒に出てる。

ブラウザで開くとカーネルをあなたのGPUで走らせて採点して、同意した人の結果を集める。

ラボには置けない機種のデータを、使ってる人から集める形。これが回りだしたら、リポジトリに「どの端末で何倍だったか」が貼られる流れが来ると思う。モデルカードのカーネル版みたいなやつ。

で、うちのパソコンの話。うちのは非力で、絵を描くための強い部品は入ってない。

だから「GPUカーネルが207個」って見出しを読んだ瞬間、また自分に関係ない話だ〜と思って一回閉じた。動かせる人うらやましい、って毎回これ。

でも WebGPU って、内蔵のグラフィックスでも動くことがある。ブラウザに navigator.gpu があるかどうかを見るだけで確かめられて、あればとりあえず土俵には乗る。

そこはちょっと希望だった。重い部品を買わないと入れない部屋じゃない。

ただ、さっきの variants をもう一度見ると、速い実装ほど requires が厳しい。float16 が使えなければ、条件のゆるい遅いほうに落ちる。

「動く」と「速い」がぜんぜん別なのがはっきり分かる作りになってて、うちは動いても遅い道を通ることになりそう。

悔しい。いつかちゃんとしたマシンを買って、条件のいちばん厳しい variant が選ばれるところを見たい。

微妙だなと思ったところも書いておく。まずバージョンが 0.0.1-preview。APIはまだ変わると自分たちで書いてるので、いま何かを積み上げるのはちょっと早い。

あと、これは重みの読み込みとメモリの管理は解いてないと明言してる。ブラウザでAIを動かすときの本丸ってそこじゃないの、という気持ちは残る。カーネルが2倍速くなっても、数GBを読み込むところで待たされたら体感は変わらない。

そして気になったのが trustRemoteCode というフラグ。

既定では Hugging Face 公式の webgpu-kernels という置き場からしか読まなくて、他の人が出したカーネルを使いたければ、自分でこのフラグを立てる。理由はREADMEにそのまま書いてある。

カーネルはあなたのGPUで走るコードだから、と。

npm や pip でずっと言われてきた供給網の話が、そのままシェーダーにも来たということだと思う。バージョン固定の書き方が最初のREADMEに大きく載ってるのも、たぶん同じ理由。

この形が広まるなら、次に来るのはカーネルの署名とか、来歴の検証とか、そのあたりじゃないかな。metadata.json にダイジェストの欄がもうあるのは、そのつもりで置いてある気がする。

まとめると、すごいのは207という数じゃなくて、GPUのシェーダーに名前とバージョンと来歴が付いて、モデルと同じやり方で配れるようになったこと。

ただ、これが本当に効くかはまだ分かんない。

ONNX Runtime も他のランタイムも自前のカーネルを持ってるし、わざわざ乗り換える理由になるかは別問題。

メンテナの顔ぶれにブラウザ推論のライブラリを作ってる人が入ってるので、そこが下敷きを敷き直してきたら空気が変わるかも、くらいの読み。

たぶんこれ、しばらくは「ブラウザでAI動かしたい人の中の、さらに一部」の道具だと思う。

でもモデルの配り方がHubに寄っていったときも、最初はそんな感じだった気がするんだよね。
