# 【ベクトルDB不要】PageIndex｜埋め込みもチャンクも使わないRAG｜758ページの本がGPUなし1コアで61秒、索引は52KB

[[tag/RAG]] [[tag/ローカルAI]] [[tag/pdf検索]] [[tag/PageIndex]] [[tag/ベクトルDB不要]]

758ページの機械学習の教科書を、GPUなしの1コアで61秒。できあがったのは52キロバイトのJSONファイル1つだけ。ベクトルデータベースは立ててないし、埋め込みモデルも1個も落としてない。

これ、長いPDFを検索する仕組みの話です。PageIndexっていう名前で、pipで入る。で、何がうれしいかっていうと、いままで「手元に500ページのPDFがあって、中身に質問したい」をやろうとすると、だいたい詰んでたんですよ。ちゃんとやるならベクトルデータベース（文章を数字の列にして近いものを探す置き場所）を用意して、埋め込みモデルを落としてきて、文書をぶつ切りにして全部ベクトル化して。わたしのパソコンは非力だから、その最初の一歩で止まる。

PageIndexはそこを全部やめてる。やめた代わりに何をしてるかというと、PDFの目次を木のかたちで取り出して、その木をLLMに歩かせる。人間が分厚い報告書を読むときに、まず目次を見て「この章だな」って当たりをつけて、そのページだけ開くやつ。あれをそのままやってる。

いままでのやり方がどこで負けてたのか

ベクトル検索って、やってるのは「似ているものを探す」なんですよね。でも検索でほしいのは「関係があるもの」で、似ていることと関係があることは別。開発元のVectify AIがそこをはっきり書いてて、わたしはこの一行でやっと腑に落ちました。似てるけど関係ないものが返ってきて、関係あるけど似てないものが落ちる。

もうひとつ、ぶつ切りにする時点で文書の構造が死ぬ。「第3章の但し書き」みたいな情報は、章の中に置かれているからこそ意味があるのに、切った瞬間にただの断片になる。わたし前にこれで痛い目を見たことがあって、同じ単語を含む別の章の部分が上位に来ちゃって、答えが微妙に違うまま平然と返ってきた。黙って間違えるのがいちばん困るんですよね。

で、ここが芯なんだけど

PageIndexが捨てたのはベクトルとチャンクだけじゃない。索引をつくるときのLLM呼び出しまで捨ててます。中を読んでいちばん驚いたのがここで、flashっていうモジュールの冒頭にそのまま書いてある。レイアウト統計からLLMなしで木を抜く、と。

実際のコードを開くと、やってることは組版の解析なんです。フォントの大きさ、太字がどれくらい混ざっているか、左に揃っているか中央か、上の行とのすきまがどれだけあるか、番号の振り方。それと「Introduction」「References」みたいな見出し語の辞書。つまり、見出しを見出しだと判定しているのは、意味の理解じゃなくてタイポグラフィ。賢さじゃなくて、太さと位置。

入れてみた

まっさらな環境にpip install pageindexで、361メガバイト、81個のパッケージ、21秒。torchもnumpyも入りません。本体のパッケージ自体は1メガバイトちょっと。

比較のために、よくある構成（sentence-transformers＋chromadb）を同じやり方で入れてみたら6,167メガバイトでした。17倍。しかもそのうち3,196メガバイトがNVIDIAのCUDA関連で、このマシンにGPUは載ってない。ここは毎回ちょっと笑っちゃう。

ただ正直に書くと、これはちょっと不公平な比べ方です。埋め込みをAPIで借りればベクトル側も軽くできる。でもその場合は全ページを外に出すことになるので、どっちを払うかという話になる。

動かした数字

リポジトリに実物のPDFが9本入ってたので、要約も最適化も切って、木を抜くところだけ測りました。758ページのPRMLが61秒で513ノード、文字数にして52,141。全文は1,732,650文字なので、33分の1まで畳まれてる。PDFそのものは18メガバイトだから、そっちと比べると350分の1くらい。

メモリは758ページで2.4ギガバイトまで上がりました。222ページの年次報告だと705メガバイト、50ページだと190メガバイト。わたしのパソコンは実効で6ギガないくらいなんですけど、この数字なら通る。珍しく「うちの子でも動く」案件で、ちょっとうれしい。開発元は9ページから1,098ページで13秒から4.5分と出してて、わたしの1コアでの測定はだいたいその線の上にいました。

9本のうち6本は、ただ栞を読んでいただけだった

ここがこの記事でいちばん書きたかったところ。出力に木の出どころが載るんですけど、9本のうち6本がbookmarks、つまりPDFがもともと持っていた栞を読んだだけでした。レイアウト解析が仕事をしていたのは3本。

えっ、と思って、栞を使うのを禁止してもう一回回しました。そうしたらPRMLは513ノードから495ノード、ほぼ変わらない。年次報告は283から291で、むしろ増えた。栞がなくても組版から復元できてる。

崩れたのは1本だけで、SECの規制文書が201ノードから54ノードになりました。4分の1。これ、中を見ると理由がわかる。法令の文書って、章の見出しが太くも大きくもないんですよ。番号と字下げだけで階層をつくってる。太さと位置を手がかりにしている仕組みは、そこで手がかりを失う。

だから、推論ベースの検索が効くかどうかを決めていたのは、推論の賢さじゃなかった。その文書の見出しが、たまたま太字で組まれていたかどうか。ちょっと気が抜けるくらい地味な分かれ目だと思う。

日本語も通ったし、壊れた入力は正直に断った

テスト用の日本語PDFを入れたら、財務ハイライト、リスク要因、今後の見通し、とちゃんと拾ってました。アラビア語とヒンディー語のものも通った。ここは英語専用だと思い込んでたので、わたしの勘違いでした。

わざと壊してもみました。PRMLの最初の3ページを画像に焼き直してPDFにしたら、ノード0個で「テキスト層がない。OCRしてから持ってこい」と返ってきた。黙ってそれっぽい木をつくらないのが好きです。バイト列を半分に切ったものはちゃんとエラーで落ちる。

捨てたぶんの代償

速さを捨ててます。ベクトル検索はミリ秒で返るけど、こっちは質問ごとにLLMが木を歩くので秒。批判もちゃんとあって、問い合わせのたびに料金がかかる、対話アプリには向かない、そして百万件の文書からどれを開くか決める仕組みがない、という指摘が出てる。最後のは本当に弱点で、ベクトルがいちばん得意なところです。開発元はファイル単位の木をもう一段上に重ねる方向で手を打とうとしてるけど、そこはクラウド版だけ。

取ったのは追跡できることだと思います。どのノードを開いて、何ページを読んで答えたのかが残る。似てる気がするから返しました、ではなくなる。

値段と入手

pip install pageindex、ライセンスはMIT、Python 3.10以上。木をつくるところはLLMを使わないので0円。要約をつけるときと検索するときだけ、自分のAPIキーのお金がかかる。設定ファイルを見たらモデル名はlitellmの書き方だと明記してあったので、provider/model のかたちで無料枠のモデルも差せるはず。ただここは鍵がないので動かせていません。確かめたのは木をつくるところまでです。

昨日も新しい版が出てて、更新はかなり速い。

これが来たなら、次はたぶん

本当の律速はテキスト層のないPDFなんですよね。だから次は、OCRのほうにも同じ発想が降りてくる気がする。大きなモデルを使わずに、組版の情報だけで文字の位置と階層を取るやつ。それと、仕様表に「ベクトルの次元数」じゃなくて「木のノード数」が載るようになるんじゃないかな。外れたらごめんなさい。

最後に、これそんなにすごい技術ではないかもしれない。新しいAIを持ってきたわけじゃなくて、何十年も前からPDFの中に入っていた組版の情報を読み直しただけです。でもわたしは、そこがいちばん気持ちいいと思っていて。賢さを足すんじゃなくて、もう置いてあるものに気づく。そういう勝ち方がある。
