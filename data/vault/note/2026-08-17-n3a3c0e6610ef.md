# AIエージェントに「コードを実行させる場所」ごと用意するOpenSandbox——DockerでもKubernetesでも動く隔離実行環境を、通信先の許可リストまで含めて配れるようにしたオープンソース

[[tag/AIエージェント]] [[tag/情報セキュリティ]] [[tag/業務自動化]] [[tag/オープンソース]] [[tag/開発環境]] [[tag/Kubernetes]] [[tag/サンドボックス]] [[tag/OpenSandbox]]

前回は、生成されたテキストの中に人の目には見えない統計的な模様を埋め込む「ウォーターマーク（電子透かし）」の話を書いた。作った側が後から「これは自分のところの出力だ」と判定できるようにする、出所の証明という一点に絞られた技術だった。その話はそこでいったん閉じる。

今回は、AIが何を出したかではなく、AIが何をどこで動かすか、の話をしたい。

私がずっと気になっていた「実行場所」の空白

エージェント（人の指示を受けて、自分で手順を分解して作業まで進めるAI）にコードを書かせるところまでは、もうどこの会社でも試している。私が引っかかっていたのは、その次の一歩だった。書かせたコードを、誰の、どのマシンで走らせるのか。

多くの現場では、これが個人のノートパソコンで起きている。エージェントが `pip install` して、どこかへ通信して、ファイルを書き換える。動くには動く。ただ、そのマシンには社内のVPN設定も、業務用の認証情報も、書きかけの資料も同居している。私自身、最初にエージェントに自動実行の権限を渡したとき、うまく動いたことよりも「今この子はこのPCの中で何でもできる状態だな」と気づいたときのほうが、ずっと肝が冷えた。

　　自宅の合鍵を渡して掃除を頼んだら、掃除機だけでなく、
　　金庫も冷蔵庫も郵便受けも開けられる立場の人を、
　　部屋の中に一人置いていた、という感覚に近い。

かといって、実行を止めれば価値はほぼ消える。調べるだけのAIと、手を動かすAIとでは、業務に対する効き方がまるで違うからだ。だから必要なのは「実行させない」ではなく「実行させる場所を、業務用の環境から切り離して用意する」ほうだと私は思っている。

そこを正面から作りにいっているのが、今日のGitHubのトレンドに上がっていたOpenSandboxというプロジェクトだった。スター（GitHub上での「いいね」に相当する印）は1万3000ほど。名前のとおり、サンドボックス——外の環境から切り離された、壊しても本体に影響しない作業場——を、AIアプリケーションのために作って配るための土台だ。ライセンスはApache 2.0で、商用利用も含めて条件付きで自由に使える形になっている。配布されているパッケージ名を見るかぎり、アリババのグループが中心になって開発しているようだ。

何がどう解かれているのか

私が面白いと思ったのは、これが「安全な箱を1種類作りました」という作りになっていない点だった。箱の硬さと、箱を配る仕組みが、はっきり分けられている。

まず、制御プレーン（コントロールプレーン。実際の作業はせず、作業場の生成・停止・後片付けだけを指揮する管理役のこと）がPythonのFastAPIというウェブ用の枠組みで立っている。ここに向かって「Python 3.12の入った箱を1つ、30分の期限つきで用意して」と頼むと、箱が1つ生まれる。

その箱を実際に作る土台は差し替え可能になっていて、いまはDockerとKubernetesの2つが実用段階とされている。Dockerは1台のマシンの中で軽い仕切りを作る仕組み、Kubernetesは何百台ものマシンをまとめて1つの大きな計算資源として扱う仕組みだ。手元で試すときはDocker、全社で運用するときはKubernetes、と同じ操作のまま移せる。

もっと硬くしたい場合の土台として、gVisor、Kata Containers、Firecrackerに対応していると書かれている。ここは用語が固まっているので開いておきたい。通常のコンテナ（アプリを必要な部品ごと1つにまとめて動かす仕切り）は、実は土台となるOSの中核部分を外の本体と共有している。つまり仕切りは薄い。gVisorはその共有部分の前に翻訳係を1枚挟んで、中のプログラムが本体のOSを直接叩けないようにする。Kata ContainersとFirecrackerはさらに踏み込んで、箱ひとつごとに極小の仮想マシン（microVM。1台のコンピュータをまるごと software で作り直したもの。ここではそれを起動が速いように極限まで削ったもの）を立てる。硬さと起動の速さは基本的に反比例するので、「どこまで硬くするか」を業務ごとに選べる形になっているのは、私には現実的に見えた。

そしてもう1つ、私が一番手応えを感じたのが通信の制御だった。箱の中に、egress（イーグレス。中から外へ出ていく通信のこと）を見張る補助コンテナが同居する。

　　部屋の外に出る扉が1つだけになっていて、
　　その扉の脇に、行き先の一覧表を持った受付が座っている。
　　一覧にない行き先を告げると、そもそも道順を教えてもらえない。

具体的には、名前解決（`example.com` のような文字列を、通信に必要な数字の住所へ変換する処理。DNSと呼ばれる）を横取りして、許可リストにない相手には「そんな住所は存在しません」という応答（NXDOMAIN）を返す。さらに厳しい設定にすると、許可された相手を解決したときに得た数字の住所だけを、通信を通す一覧へ有効期限つきで動的に足していく。既定は全部禁止、書いたものだけ許可、という向きだ。`*.pypi.org` のようにまとめて許す書き方もできる。

[エージェント / 業務アプリ側]
        │  SDK・CLI・MCP 経由の呼び出し
        ▼
┌──────────────────────────────┐
│ 制御プレーン（管理役）       │  作成・停止・一時停止・再開
└──────────────────────────────┘
        │  ここが差し替え可能
        ▼
     Docker  ／  Kubernetes
        │
        ▼
┌──────────────────────────────┐
│ サンドボックス 1つ           │
│  ├ 実行デーモン              │ コマンド実行・ファイル操作・コード実行
│  └ 通信監視の補助コンテナ    │ 行き先の許可リストを強制
└──────────────────────────────┘
   さらに硬くしたい場合の土台：
   gVisor ／ Kata Containers ／ Firecracker

　　要するに、箱を作る係と、箱の硬さと、
　　箱から外に出る扉の管理が、それぞれ独立して選べる。

一時停止と再開もある。Kubernetes上では、内部的にスナップショット（ある瞬間の状態をそのまま写し取ったもの）として保存され、稼働中→停止処理中→停止→再開処理中→稼働中、と状態が移る。使っていない箱を止めておいて、続きから再開できるということだ。

これは以前に書いた、エージェントに与える「計算機そのもの」を作り直す話と地続きだと思っている。あのときは、エージェントが触るファイルシステムをデータベースの中に作り直し、実際にコードを走らせる部分だけ後から差し替えられるようにする、という設計を扱った。今回のものは、その差し替えられる側——実行そのものを引き受ける部分——を、どの会社でも自前の環境に立てられる形で切り出したものに見える。エージェントに何をさせるかという議論の下で、静かに「エージェント用の計算機をどう調達するか」という層が独立した産業になりつつある、という感触が私にはある。

実際に触るとしたら

導入は拍子抜けするほど短い。Pythonの3.10以降が入っていれば、パッケージを入れて、設定ファイルを初期化して、箱を1つ作るところまで数行で届く。

pip install opensandbox-cli
osb config init
osb sandbox create --image python:3.12 --timeout 30m -o json

プログラムから使うための部品（SDK。開発者が自分のアプリに機能を組み込むための道具一式）は、Python、Java、JavaScript/TypeScript、C#、Goが用意されている。加えてMCP（Model Context Protocol。AIが外部の道具を呼び出すための共通の作法）に対応したサーバーも同梱されているので、対応するAIアシスタントからそのまま「箱を作って、この処理を走らせて」と頼める。管理情報は手元の小さなデータベースに保存され、設定は1つのテキストファイルで済む。試すだけなら、その日のうちに終わる規模だと思う。

できないこと、気をつけたいこと

ここは隠さずに書いておきたい。

硬い隔離を選ぶ場合、gVisorやKata Containers、Firecrackerは土台側の準備が別途必要になる。「対応している」は「入れれば動く」ではなく「受け皿がある」に近い。

通信の見張りには、ネットワーク設定を書き換える特別な権限が要る。そしてドキュメントには、その権限がない場合は警告を出したうえで強制を無効にする、と書かれている。落ちないのは運用上ありがたい一方、権限の付け忘れに気づかないまま「守られているつもり」で走り続ける事故は起こりうる。私なら、ここは必ず検知の仕組みを別に置く。

暗号化された通信の中身まで見にいく機能は、明確に実験的と書かれていて、動作もインターフェースも変わりうるとされている。本番の統制をここに寄りかからせるのは、いまは早いと思う。

外部から中の箱へ安全に接続する機能は、Kubernetesで特定の入口経由で公開した場合にだけ効く、という限定がある。Dockerで手元に立てた構成では同じようにはならない。

そして、「速い」とは書かれているが、起動時間やオーバーヘッドの具体的な数字は私が見た範囲では出ていない。ここは自分の業務の形で測るしかない。1日に何万回も箱を作り捨てる使い方なら、この測定が導入可否をそのまま決めると思う。

これは何のコストを消し、誰の仕事を変えるのか

私の見立てでは、消えるのは「各チームが自前でエージェント実行環境を作る」という、社内で何重にも重複していた仕事だ。開発チームがDockerを薄く包んだ道具を書き、データ分析チームが似たものをもう1つ書き、業務部門が別の何かを立てる。それぞれが独自に権限設計をして、それぞれが独自に穴を空ける。この重複と、そこから生まれるばらつきが減る。

減らないどころか増えるのは、許可リストを設計し、審査し、更新する仕事だ。「このエージェントはどこと通信してよいか」という問いは、技術の問題であると同時に業務の問題で、答えられるのは現場の担当者しかいない。私は、これが情報システム部門の定常業務として定着していくのではないかと思っている。棚卸しの対象が、サーバーやアカウントから、エージェントの行き先一覧へ広がる、という形で。

効いてくる業務も、想像より地味なところからだと私は見ている。請求データの突合、社内の書類変換、定型レポートの生成——外部に出せないデータを扱い、しかも作業が機械的な仕事だ。こういう業務は、外部のサービスに投げにくいという一点だけで自動化が止まっていることが多い。自社の中に安全な作業場を立てられるなら、その障害がひとつ外れる。

もっとも、これを入れれば安全になる、という話ではまったくない。箱を用意することと、箱の中で何が起きたかを記録し、説明できるようにすることは別の課題だ。後者について私はまだ十分に理解できていないし、この道具がそこまで面倒を見てくれるとも思っていない。それでも、「実行させるかどうか」で止まっていた議論を、「どういう条件で実行させるか」へ動かす材料としては、かなり手触りのよいものが出てきたと感じている。

週末に自分の環境で立ててみて、いちばん硬い設定のときに起動が何秒かかるのかを測るところから始めるつもりでいる。
