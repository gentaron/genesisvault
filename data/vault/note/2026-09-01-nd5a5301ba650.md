# 「AとB」では書けない関係を、1本の線でまとめて掴む——文章を知識グラフとハイパーグラフに変換するオープンソースCLI「Hyper-Extract」を実際に動かして確かめた話

[[tag/AI]] [[tag/python]] [[tag/情報整理]] [[tag/オープンソース]] [[tag/RAG]] [[tag/ナレッジマネジメント]] [[tag/知識グラフ]] [[tag/ハイパーグラフ]]

3人で1つの実験をやった、という一文がある。

これを機械が読める形に落としたい。素直にやると、こうなる。AとBが共同した。BとCが共同した。AとCが共同した。線が3本できる。

でも、これは起きたことと違う。現実に起きたのは「3人で1つ」であって、「2人組が3つ」ではない。しかも、この書き方だと4人になった瞬間に線は6本、5人なら10本に膨らむ。事実は1件なのに、記録だけが増えていく。

私はここで、はっきり手が止まった。ずっと当たり前だと思って使っていた形式が、当たり前ではなかったからだ。

三つ組という、あまりに強い前提

知識グラフという言葉がある。つまり、文章を「点」と「線」に描き直したもののことだ。中身は三つ組（トリプル）で書かれる。「誰が」「どうした」「誰に」の3点セット。この形は検索に強いし、扱いも軽い。だから長いあいだ標準だった。

ただ、三つ組は必ず2つの点しか結べない。線の両端は2つまで、という決まりが最初から入っている。

　　二人乗りの自転車を何台並べても、8人が乗ったバスにはならない。

会議、共同研究、取引、訴訟、合併。人が3人以上そろって初めて成立する出来事は、世の中の書類のほとんどを占めている。それを全部、2人ずつに割ってから記録していた。私はこの構造をずっと素通りしていた。

1本の線に、何人でも入れる

Hyper-Extract は、この前提を外しにいくCLIツールだ。文章を投げると、知識グラフだけでなく超グラフ（ハイパーグラフ）として構造化してくれる。

超グラフというのは、線が3つ以上の点を同時に束ねられるグラフのこと。その線を超辺（ハイパーエッジ）と呼ぶ。つまり、「この会議に出たのはこの5人です」を、5人ぶんまとめて1本で書ける。

実際に手元で走らせて、書き出されたファイルを開いてみた。辺のデータはこうなっていた。participants（参加者）という名前のリストがあり、そこに関係者の名前が並ぶ。あとは説明文、キーワード、そして強度を表す数値。始点と終点という欄がそもそも存在しない。

小さいことだが、私はここで少し笑ってしまった。「両端」という発想を消すだけで、記録の形がこんなに変わる。

もう1つ、地味だが効く設計があった。書き出された索引が2つに分かれている。点の索引と、辺の索引だ。ふつうの検索は「登場人物」を探す。この作りだと「関係そのもの」も直接探せる。つまり、「田中さん」ではなく「田中さんが関わった合意」を引きにいける。

動かすのに何が要るのか

ここは具体的な数字で書いておく。

必要なのは Python 3.11 以降。配布物が想定しているのは 3.11 と 3.12 で、3.10 以下は入らない。インストールは pip で1行、あるいは uv や pipx でも入る。ライセンスは Apache 2.0。最新版は 0.4.0 で、2026年8月1日公開。最初の版が2026年4月4日なので、まだ5か月ほどの若いプロジェクトだ。星は3,000ほど付いている。

GPUは要らない。これが一番効く。依存に入っているのはCPU版のベクトル検索ライブラリと、軽量な埋め込みモデルと、LLM呼び出しの薄い層だけ。PyTorchもCUDAも入ってこない。

実測してみた。仮想環境を作って入れ切った状態で、ディスクは約493MB。コマンドを1回叩いたときのピークのメモリは約99MB、起動は1.2秒。文章の取り込みと索引作成まで一気に通したときでも、ピークは約166MB、所要2.8秒だった（モデルの応答を差し替えて配線だけを通した計測なので、実運用での待ち時間はほぼ全部、APIの応答待ちに乗ると考えたほうがいい）。書き出されたデータ一式は40KBだった。

OSは選ばない。CPU版のベクトル検索ライブラリはWindows向けの配布物が Python 3.10 から 3.14 まで用意されていて、macOSとLinuxも揃っている。残りの依存は全部OSを問わない形式だ。Windows、macOS、Linuxのどれでも、3.11か3.12を用意すれば動く。

代わりに要るのが、LLMのAPIキーだ。OpenAI、Anthropic、DeepSeek、Alibaba Bailian、それから自前で立てた vLLM に対応している。埋め込みだけはOpenAI互換の口が必要で、AnthropicとDeepSeekは埋め込みAPIを持たないので別のものと組み合わせる。ここは完全ローカルではない。作者側の見積もりでは1ページあたりDeepSeekで0.001〜0.005ドル、gpt-4o-miniで0.01〜0.05ドル。あくまで作者の見積もりであって、私が測った数字ではない。

もう1つ、実際にぶつかった落とし穴を書いておく。初回実行時、トークン数を数えるための辞書ファイルをネットから取りに行く。外に出られない環境だと、ここで止まる。事前にキャッシュを置いておく必要がある。

「効く」と言えるのか

超グラフにする意味は、査読を通った形で一度検証されている。2026年4月27日に Nature Communications に載った Hyper-RAG の論文だ。

医療分野のデータセットで、LLMに直接聞く場合より12.3%、GraphRAGより6.3%、LightRAGより6.0%の精度向上。質問が複雑になるほど差が開き、優位は12.7%から15.0%に広がったとある。仕組みの側の指標もあって、重要な知識の取りこぼしが35%減、幻覚（もっともらしい嘘）の発生率が50%減、誤りが後段に伝播する係数が0.59から0.14へ76%減。軽量版は検索速度が2倍で、それでも3.3%上回ったという。

数字だけ見れば強い。ただ、別の見方をすれば、この数字の読み方はもう少し慎重でいい。

9つの分野を平均して「LightRAGより35.5%改善」という数字が出てくるが、これは選択式の判定による評価だ。正解と一字一句照合する精度とは意味が違う。金融で37.5%、法務で55.3%という幅の広さも、測り方が効いている証拠だと私は思う。

そしてもっと大事なこと。この Hyper-Extract を作っているのは、Hyper-RAG を書いた研究グループと同じだ。ツールの中には9つの手法が並んでいて、他グループの超グラフ実装も binary な従来手法も一緒に入っている。作りとしては公平だ。それでも、既定で最も光る手法の性能を測ったのが同じ人たちである、という事実は消えない。誰が、どんな条件で測ったのか。ここは自分で確かめる余地が残っている。

反対側の言い分もはっきりしている。2つの点しか結ばない従来のグラフは、抽出が軽くて安い。文章を切って埋め込むだけの素朴なやり方は、もっと安い。超辺を作るということは、LLMに「この文の中で、誰と誰と誰が同じ出来事に属しているか」を毎回判定させるということで、そのぶん確実に手間とお金が増える。論文の著者自身も、切れ目をまたいだ関係の抽出が難しく、後処理での統合が要ると認めている。

分かれ目は精度ではなく、扱う文章の性質のほうにある気がしている。登場人物が2人で完結する文章なら、超辺はただの重い装飾だ。3人以上が同時に絡む文章が多いなら、話が変わる。

捨てられているもの

正直に書いておくと、私が一番引っかかったのはここだ。

同梱されているテンプレートは46個。内訳は分野別の知識テンプレートが37個（一般12、金融5、産業5、法務5、医療5、中医学5）と、抽出手法が9個。この37個すべてが、対応言語として中国語と英語だけを宣言している。日本語のテンプレートはない。コマンドの言語指定も中国語か英語だ。

日本語の文章を入れて動かないわけではない。判定するのはLLMだから、モデルの多言語能力に乗る形にはなる。ただ、項目の説明文が英語や中国語で書かれたまま日本語を読ませることになるので、設計者が意図した精度が出る保証はない。本気で使うなら、自分でYAMLのテンプレートを1枚書くことになる。書式自体は素直なので、そこは難しくない。

もう1つ。公式の説明には80以上のテンプレートと10以上のエンジンとあったが、実際にインストールされたものを数えたら46だった。開発中の枝と配布物で数が違うのだと思う。こういう食い違いは、README1行の但し書きで評価がひっくり返ることがあるので、自分の手元で数えるに越したことはない。

何のコストが消えるのか

ビジネス側の話をすると、消えるのは「書類を読んで、誰が何に関わったかを表に起こす」あの作業だ。契約書、議事録、症例、決算資料。人が読んで台帳に転記していた工程が、コマンド1つに寄る。しかも追記ができるので、新しい書類を足すたびに知識の側が育っていく。

代わりに増えるコストもはっきりしている。APIのトークン代。テンプレートを自分の業務に合わせて設計する手間。そして、出てきた構造が本当に正しいかを確かめる工程。ここを飛ばすと、間違った関係が整った形で残るという、いちばん厄介なものが出来上がる。

私はまだ、これが定番になるとは思っていない。三つ組という形式が長く生き残ってきたのには、軽さという理由がちゃんとあった。それでも、「両端は2つまで」という制約を疑ってみる価値があることは、参加者リストが並んだあのファイルを見た時点で、私の中では決まってしまった。

自分がふだん扱っている文章を思い浮かべてほしい。そこに出てくる出来事は、2人で閉じているだろうか。それとも、いつも誰かがもう1人いるだろうか。
