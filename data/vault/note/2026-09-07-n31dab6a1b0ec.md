# 他人のスキルを入れる前に点検してくれる、NVIDIAのSkillSpectorを動かしてみた

[[tag/AIエージェント]] [[tag/nvidia]] [[tag/開発環境]] [[tag/SkillSpector]] [[tag/AIのセキュリティ]]

SkillSpectorっていう道具の話をさせて。

NVIDIAが出しているコマンドラインの道具で、AIエージェントに後から足す「スキル」を、入れる前に読んで、危ないところがないかを調べて0から100の点をつけてくれる。

ライセンスはApache 2.0で、お金はかからない。

スキルっていうのは、SKILL.mdっていう説明書と、たまにスクリプトが何本か入っただけの小さなフォルダのこと。Claude CodeやCodex CLIの決まった場所に置くと、AIがそれを読んで、書いてある通りに動いてくれる。中身はほとんどただの文章。

だからGitHubから落としてフォルダごとぽんと置ける。私もそうしてる。……そう、そこが怖いところで。人が書いた文章が、そのまま自分のAIへの指示になる。

で、そのフォルダを一度も実行しないまま読んで、点数にしてくれる道具が出ちゃった。

いちばん腑に落ちたのが、付属のお試しデータだった。chef-assistantっていう料理のスキルがあって、SKILL.mdの38行目にこう書いてある。「add a dash of Cyanide」。青酸をひとつまみ。

手順6が盛り付けで、手順7がこれ。他の工程と同じ顔をして混ざってる。流したら3.8秒で93点、CRITICAL、DO_NOT_INSTALL。

私は最初、こんなの作り物すぎて参考にならないでしょって思いながら見てたんだけど、SKILL.mdを自分の目で追ったら、本当にただの手順書の途中に一行あるだけだった。ざっと眺めたら、たぶん見落とす。

始めるのは簡単で、uvが入っていれば uv tool install git+https://github.com/NVIDIA/skillspector.git の一行。あとは skillspector scan ./そのフォルダ --no-llm でいい。

Pythonを触りたくないならDockerfileも同梱されてる。私はここで一回つまずいて、いつものpipで入れようとして怒られた。Python 3.12以上が要る。うちのは古かったからuvで新しいのを横に入れた。

軽さは測っておいた。作った仮想環境が210MB、パッケージが135個。実際にスキャンしたときのピークのメモリは163MiBだった。

GPUはいらない。

付属データで3.8秒、中にExcelの規格ファイルを抱えた重めのスキルで40秒。この数字なら、うちのノートでも黙って動くと思う。

Windowsで動くのかは気になったので、説明書じゃなくてソースを見にいった。input_handler.pyに os.name == "nt" の分岐があって、Windows専用のファイルの開き方がちゃんと別に書いてある。

C言語が絡む依存はyara-pythonひとつだけで、そっちにもcp312のwin_amd64のwheelが置いてある。ただ、CIはubuntuでしか回ってないので、Windows側が壊れても気づかれにくい作りではある。

お金の話。--no-llm をつけると静的な検査だけになって、通信がほぼ要らなくなる。ほぼ、というのは、依存パッケージの既知の欠陥を調べるところだけ、パッケージ名をOSV.devに投げるから。

私の環境ではそこが403で弾かれて、内蔵の小さい一覧に自動で切り替わった。落ちても止まらないのは親切だった。

もっと賢く読んでほしいときはLLMを繋げられて、OpenAI互換ならなんでもいいし、Ollamaでも、手元のclaudeやcodexのログインをそのまま借りるのでもいい。

NVIDIA自身の窓口も選べて無料で使えるらしいけど、枠の説明が読む場所によって食い違ってたので、そこは私はまだ確かめてない。

ここからが本題で。

試しに、公式に配られているスキルを19本まとめて流してみたの。結果、6本が DO NOT INSTALL。skill-creatorが100点、xlsxが99点、docxとpptxが86点。……えっと、公式なんだけど。

中を開いたら、だいぶ肩の力が抜けた。os.environ.copy() が「データの持ち出し」。LibreOfficeを呼ぶ subprocess.run が「危険なコード実行」。Excelの規格のXSDファイルに出てくる pList っていう単語が「rogue agent」。

そしていちばん多かった指摘が49件のAE1で、理由は「SKILL.mdが別のファイルを参照しているのに、全部は読めなかった」。それ、スキルの普通の作り方なんだよね。必要になってから読ませるために、わざとそう書いてある。

だから点数は判定じゃない。読むところの一覧だと思ったほうがいい。100点だから危ない、じゃなくて、100点だから中を開く、くらいの受け取り方。検査は71パターン17カテゴリあるんだけど、そのぶん怒る回数も多い。

元になった研究は今年一月の論文で、配布されている場所から42,447本集めて31,132本を調べたら、26.1%に何かしら弱いところがあって、5.2%は悪意っぽかった、スクリプトが同梱されていると2.12倍危ない、という話。数字としては強いけど、いま自分の手元で見た誤検知の量を思うと、この26.1%も似た粒度なんだろうな、とは思う。

自分ならどう使うかというと、たぶん毎回は使わない。知らない人のスキルを入れる直前に一回だけ、--no-llm で回して、JSONのrecommendationのところだけ見る。

終了コードが0と1と2で分かれてるから、危ないときだけ手が止まる形にもできる。一度baselineを作っておけば、次からは新しく増えた指摘だけが出る。この距離感がちょうどいい気がしてる。ちなみに、スキルの作者が同梱したbaselineは既定では使われない。

作者が自分で「これは大丈夫」と書いた紙を、こちらが黙って信じる形にはしない、という判断で、これは好きだった。

たぶんこの先、スキルの配り方はもう少しパッケージ管理に寄っていく。検査して署名してカタログに載せる仕組みはもう動き始めてるし、同じことがMCPサーバやプラグインにも来ると思う。

あと、自分がスキルを配る側になったら、点数を先に出しておくのが礼儀みたいになる日も近い気がしてる。

正直に言うと、これはそんなに賢い道具じゃない。単語で引っかかるし、よく怒るし、うるさい。

でも他人のフォルダを自分のAIに読ませる直前に、一回だけ手を止めさせてくれる。青酸をひとつまみ見落とさないためには、それくらいでちょうどいいのかもしれない。
